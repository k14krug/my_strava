# P1-03 — Activity Review Experience and Phase 1 Acceptance

**Status:** Analyst-authored JIT; implementation not started  
**Phase:** Phase 1 — Useful single-ride review  
**Task:** P1-03  
**Controlling product:** RideWorks

## 1. Purpose

Build the first real RideWorks browser experience: a rider-facing Activity Review page for the representative ride that uses the accepted P1-01/P1-02 evidence and analysis, follows the approved Activity Review mockup, and is useful enough to answer:

> How did this ride go?

P1-03 is the Phase 1 product slice. It should turn the already-trusted Activity/Source/analysis package into a practical local application screen without pulling later RideWorks capabilities forward.

This task also defines the first usable RideWorks journey: start the local application, see/select the imported activity, open it, review it, and reopen it after restart.

P1-03 ends with Owner visual/usability review and final Analyst closeout for Phase 1.

## 2. Background / question being answered

P1-01 established durable application-owned ride evidence.

P1-02 established one trusted analysis package containing:

- Activity, FIT Source and current extraction identity;
- source-backed FIT session summary;
- unchanged native timestamp/power/HR records;
- signal availability;
- application-derived best 20-minute power with explicit method/version context.

The remaining Phase 1 question is not architectural:

> Can RideWorks present that evidence clearly enough that the rider can review this ride in a browser without needing Strava?

The approved visual reference is `docs/mockups/activity-review.png`.

The screen should grow into that mockup over later phases, but P1-03 must show only capabilities that actually exist now.

## 7. First usable RideWorks journey

Phase 1 uses the already-implemented CLI import path.

The required user journey is:

1. import the representative FIT into a RideWorks data directory using the accepted P1-01 command;
2. start the RideWorks local browser application using the same data directory;
3. open the URL printed by the server;
4. see the imported activity in an Activities list/landing page;
5. open the Activity Review page;
6. review the ride summary, native power/HR chart and best 20-minute result;
7. stop and restart RideWorks;
8. reopen the same Activity through the list or stable Activity URL without re-importing the FIT.

Expected CLI shape:

```bash
python -m rideworks --data-dir <data-dir> serve
```

Exact optional port spelling is implementation discretion.

### Local server boundary

By default:

- bind to loopback only (`127.0.0.1` / localhost);
- do not expose the application on all network interfaces;
- print the local URL clearly;
- do not add authentication merely for this local single-rider Phase 1 slice.

A port override is acceptable. Remote/network hosting is not part of P1-03.

## 8. Required implementation

### 8.1 Web/application boundary

Add a small RideWorks web boundary independent of the retired Strava runtime.

Prefer:

- server-rendered HTML;
- ordinary CSS;
- minimal browser JavaScript needed for the chart and local presentation;
- no frontend compile/build step.

The page must consume the accepted RideWorks Store / `analyze_activity` application boundaries. UI code must not:

- parse FIT files;
- recalculate best-20 independently;
- read research reports;
- query Strava;
- pull values from the retired application database;
- silently replace missing evidence.

A small additional Store read helper to list activities is allowed. Keep it narrow; do not create a generic repository framework.

### 8.2 Activities landing/list page

The root page should provide a working way to open imported activities.

For each stored Activity with usable Phase 1 FIT evidence, show enough to identify it, using available source evidence such as:

- date/time;
- cycling/sub-sport label;
- compact distance/duration context when available.

For Phase 1, a simple list/card is enough.

Clicking an Activity opens its stable Activity Review URL keyed by RideWorks Activity ID.

If the store contains no activities, show a useful empty state with the existing CLI import command concept. Do not invent browser upload.

Do not show Dashboard or other non-working navigation destinations.

### 8.3 Application shell and navigation

Follow the approved mockup's persistent-left-shell direction.

For Phase 1 the shell should include only real capabilities:

- RideWorks identity/wordmark/mark area;
- Activities as the one real navigation destination.

Do not include inert Dashboard, Performance, Training Plan, AI, notification, sync, account/profile or settings controls.

The shell should be designed so later destinations can be added without redesigning the page, but do not build the later navigation now.

### 8.4 Activity identity/header

The Activity Review header must show:

- RideWorks Activity identity in a secondary/inspectable form;
- activity date/time;
- cycling/activity type/sub-type available from FIT;
- FIT/source context.

Because there is no polished activity-name system yet, use a sensible source-derived label such as “Virtual Ride” rather than inventing a title.

The browser/document title should use RideWorks and identify the activity.

### 8.5 Display units and formatting

Phase 1 uses a fixed presentation policy rather than adding settings.

Normal rider-facing presentation:

- distance: miles;
- ascent: feet;
- power: watts;
- heart rate: bpm;
- cadence: rpm;
- duration: human-readable `h:mm:ss` or `m:ss` as appropriate;
- best 20-minute result: the accepted whole-watt P1-02 value;
- source average/max integer sensor summaries: show as supplied, with units;
- missing values: “Unavailable” or an equally clear nonnumeric label.

Do not modify stored source units. Conversions are presentation-only.

Suggested precision:

- distance: two decimals for this Phase 1 ride;
- ascent: nearest whole foot;
- watts/bpm/rpm: whole units when the source/derivation is integer-presented.

### 8.6 Date/time and chart time

Activity header date/time should be shown in the browser's local timezone and visibly identify the timezone/offset so it is not ambiguous.

Do not rewrite persisted timestamps.

For the time-series chart:

- use elapsed ride time on the x-axis;
- preserve each native record timestamp/order;
- do not resample, interpolate, smooth or manufacture points.

Elapsed-axis presentation is a display transformation only; the source timestamps remain available in the analysis package/details.

### 8.7 Top ride metrics

Use a compact top row of prominent metrics consistent with the mockup.

For Phase 1, favor the most useful available facts rather than cramming every summary field into cards.

A suitable minimum set is:

- elapsed duration;
- distance;
- average power;
- average heart rate.

Best 20-minute power belongs in its own supporting performance panel rather than being presented as though it were a FIT source summary.

Other required source summary values may live in the right-hand Ride Summary panel.

### 8.8 Power & heart-rate chart

The central chart is the primary body of the page.

It must show:

- power over elapsed time;
- heart rate over elapsed time;
- both signals distinguishably;
- all native Phase 1 records in their original temporal relationship.

Minimum interaction:

- hover or pointer inspection of the nearest native sample;
- tooltip/readout showing elapsed time, power and heart rate for that sample;
- clear legend/axis labels.

If a value is missing, do not draw an invented/interpolated value through it.

No zoom, brushing, smoothing, zone shading, interval overlays or map linkage are required.

For the representative ride, the chart should render all 3,621 native records without changing analytical values.

### 8.9 Best 20-minute panel

Show the accepted P1-02 best-20 result as an **application-calculated** result.

For the representative ride this should display the P1-02 rounded value while retaining inspectable context.

The panel should distinguish it visually/textually from FIT source summaries.

Do not add comparison arrows, PR claims, FTP percentages or “good/bad” interpretation.

### 8.10 Ride Summary panel

Use a right-hand summary panel consistent with the mockup to show remaining available source-backed facts, including:

- elapsed duration;
- timer duration, labeled separately;
- distance;
- ascent;
- average/max power;
- average/max heart rate;
- average cadence.

Avoid unnecessary duplication where the top cards already show a value, but both elapsed and timer duration must remain distinguishable somewhere visible.

Unavailable values must remain visibly unavailable.

### 8.11 Provenance / inspectability

Provide a secondary details area, drawer, disclosure or panel that does not clutter the normal ride review.

It must make practical inspection possible for at least:

- Activity ID;
- Source ID;
- original basename;
- artifact SHA-256 and byte size;
- packaging/content format;
- parser/version;
- RideWorks mapping version;
- current extraction ID;
- power/HR availability counts and origin classification;
- statement that the ride summary values shown are FIT session source evidence;
- best-20 origin = application-calculated;
- best-20 method/version;
- best-20 sample count/start/end context.

Do not expose:

- private absolute source paths;
- database paths;
- coordinates/raw location data;
- secrets.

The details area may show raw source UTC timestamp strings if useful, clearly labeled as source detail.

Where practical, include a favicon/browser icon derived from the approved mark. Do not create native launcher packages.

### 8.13 Visual direction

Use `docs/mockups/activity-review.png` as the visual/layout authority.

Preserve:

- empty store shows a useful import-oriented empty state;

- metre-to-mile and metre-to-foot display conversions are tested;
- duration formatting is tested;
- browser/local-time presentation has explicit timezone labeling or metadata supporting it;
- source values remain unchanged by display conversion.

#### Shell

- RideWorks appears in page/browser identity;
- Activities is a working navigation destination;
- prohibited fake Phase 1 controls/destinations are absent.

1. RideWorks starts as a local browser application without depending on the retired Strava runtime.

2. implementation would require a new analytical metric or source-selection policy;
3. a browser upload workflow appears necessary rather than merely convenient;
4. a new account/authentication/network-access decision is required;
5. the approved mockup cannot be followed for a concrete technical/data reason;
6. settled branding assets conflict materially with the approved page direction;

Straightforward implementation/UI defects and Owner-requested presentation corrections within this page may be fixed and re-verified without reopening the product architecture.
