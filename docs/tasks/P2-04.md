# P2-04 — Prior Six-Week Context in Activity Review

**Status:** Analyst-authored JIT; implementation not started  
**Phase:** Phase 2 — Historical context and performance history  
**Task:** P2-04  
**Controlling product:** RideWorks

## 1. Purpose

Put an eligible ride's trusted 20-minute result into immediate recent context inside Activity Review.

P2-03 established the trusted Virtual Ride/native-power cohort and durable Performance history. P2-04 should answer one narrower question when reviewing a ride:

> How does this ride's best 20-minute power compare with my best eligible result in the prior six weeks?

This is historical context, not training-state interpretation. The result should be factual, neutral, explainable and linked back to the trusted Performance evidence.

## 4. Store/data rule

P2-04 operates on the **accepted RideWorks store**.

It must **not**:

- reopen or re-import the historical Strava archive;
- rebuild the durable Activity/source store from the archive;
- reparse the 1,421 historical source artifacts merely to calculate this comparison;
- automatically run `rebuild-performance` during page rendering or server startup.

Use the already persisted P2-03 trusted performance history and current RideWorks metadata.

For local acceptance, make a disposable copy of the accepted full-history P2-03 RideWorks store. Do not create the P2-04 review store by re-importing the Strava ZIP.

If trusted Performance history is stale/missing for an Activity, show the comparison as unavailable with an honest reason. Do not silently rebuild it as a side effect of opening Activity Review.

## 5. Comparison eligibility

The comparison applies only when the current Activity has a **current eligible P2-03 trusted Performance result** under:

- policy: `virtual-native-power-v1`;
- method: `best-average-power-v1`;
- duration: 1,200 seconds.

The current ride's ordinary rich FIT Activity Review may still show its own on-demand best-20 result even when it is not eligible for trusted Performance history.

Do not treat that ordinary best-20 result as trusted historical context unless the Activity also has a current eligible P2-03 Performance result.

Examples:

- eligible Virtual Ride + current persisted trusted result → comparison may be available;
- outdoor Ride with best-20 → trusted recent comparison unavailable;
- Virtual Ride whose persisted Performance result is stale/pending → comparison unavailable until Performance history is rebuilt;
- thin GPX/TCX/CSV-only review without supported rich best-20 → no fabricated comparison.

## 6. Prior-six-week window

For current eligible Activity start time `t`, define the prior comparison window as:

```
(t - 42 days, t)
```

That is:

- exactly the 42-day rolling interval immediately before the current Activity;
- the current Activity is excluded;
- an Activity exactly 42 days old at `t` has expired from the window;
- this matches P2-03's accepted rolling-42-day expiry semantics.

Only prior current eligible results under the **same policy/method/duration** may participate.

A result must have an established absolute Activity start time to participate in this exact timed window. Do not invent timezone placement for source dates whose timezone is unknown.

## 7. Prior best selection

Among eligible prior results in the window:

1. compare **raw unrounded best-20 average watts**;
2. highest raw average wins;
3. if raw averages tie exactly, choose the earliest Activity start;
4. if still tied, use stable RideWorks Activity ID as deterministic final ordering.

Retain enough context to identify:

- current Activity/result;
- prior-best Activity/result;
- raw and displayed watts;
- prior Activity start/date/title;
- exact comparison-window start/end;
- method/policy/duration.

This is a cheap read-time comparison over durable P2-03 results. Do **not** add a new persisted comparison table unless implementation uncovers a concrete need; if that happens, stop and report rather than silently adding generalized analytical persistence.

## 8. No-baseline and unavailable cases

If the current Activity is eligible but no eligible trusted result exists in the prior window:

- show **Prior 42-day best: Unavailable**;
- explain concisely that no qualifying prior result exists in the preceding six weeks;
- do not substitute an older lifetime/year result;
- do not substitute summary watts;
- do not display zero.

If the current Activity itself is not in current trusted Performance history:

- show trusted recent context as unavailable only where that context belongs naturally in the rich Activity Review;
- explain the narrow reason without overwhelming the normal ride review;
- do not imply that the ride's own best-20 calculation is invalid merely because it is excluded from the trusted longitudinal cohort.

If Performance history is stale/pending, state that trusted context requires a Performance rebuild. Do not trigger one automatically.

## 9. Activity Review presentation

Integrate the context into the existing rich Activity Review without redesigning the page.

The existing best-20 result remains the primary ride calculation.

Near the **Best 20-minute power** panel, add a visually distinct comparison block whose purpose is obvious without prior knowledge of P2-04.

Use a clear rider-facing heading such as:

**Compared with previous 6 weeks**

The block must show at minimum:

- **This ride:** displayed best-20 watts;
- **Prior 42-day best:** displayed watts or Unavailable;
- a neutral displayed watt difference when a baseline exists, e.g. **95 W below** / **5 W above** / **Same displayed watts**;
- date/title or compact identity of the prior contributing Activity when available;
- an explicit **Open prior ride** link/action;
- a **View Performance** link to `/performance`.

The comparison must be visually prominent enough that a rider opening Activity Review can immediately tell that recent historical context has been added. It should not read like provenance, footnote text, or a minor metadata row.

A compact inset card/band inside the existing Best 20-minute power panel is preferred; a separate full-width major panel is unnecessary unless that proves clearer.

The comparison should be understandable within a few seconds without requiring expansion of details.

### 9.1 Neutral presentation

Presentation must remain neutral.

Allowed factual language includes:

- `5 W above prior 42-day best`;
- `3 W below prior 42-day best`;
- `Same displayed watts as prior 42-day best`.

Do not use:

- green/red good/bad semantics;
- arrows implying improvement/decline unless they are purely directional and visually neutral;
- language such as `great`, `poor`, `fitness improved`, `fitness declined`, or training recommendations.

A numeric difference is **required when a prior baseline exists**, because it makes the comparison immediately legible. Derive it from the two raw averages, display it as a neutral comparison, and do not persist it as a new durable metric.

Do not show a percentage difference unless it materially improves understanding; it is not required.

## 10. Performance link behavior

Activity Review must link naturally to the accepted Performance page.

A simple link to the relevant Performance view/range is sufficient, for example a recent Rolling 42-day view. P2-04 does not require adding a generalized selected-Activity deep-link protocol to Performance.

If a small selected-Activity query parameter can be added cleanly without complicating the accepted P2-03 behavior, it is allowed but not required.

Do not change Performance's trusted eligibility or aggregation semantics.

## 11. Provenance / inspectability

The recent-context details must make the basis inspectable without cluttering the normal view.

A compact details disclosure may show:

- policy `virtual-native-power-v1`;
- method `best-average-power-v1`;
- duration 1,200 seconds;
- current Performance result Activity/Source/extraction identity;
- prior-best Activity/Source/extraction identity;
- raw current/prior averages;
- exact prior-window bounds;
- explicit statement that the current Activity is excluded from its own baseline.

Do not expose private local filesystem paths or native record streams.

## 12. Date/time behavior

Use established absolute Activity start times for the exact 42-day membership calculation.

Display dates/times under the accepted P2-02/P2-03 browser-local presentation policy.

Persisted source timestamps remain unchanged.

If current Activity time is not absolute, do not guess an exact 42-day window; show trusted recent context unavailable.

## 13. Existing Activity Review behavior

P2-04 must not weaken accepted Phase 1/P2-02 behavior.

For the representative rich FIT Activity:

- source title remains preferred;
- FIT session summary remains attributable to FIT;

- provenance remains inspectable.

For thin TCX/GPX/CSV-only/ambiguous-FIT Activity Reviews:

- do not fabricate current best-20 or recent context merely to fill the page.

## 15. Automated tests

Add focused tests covering at least:

### Window semantics

- prior window is exactly `(t - 42 days, t)`;
- current Activity is excluded;
- result one second/instant inside the 42-day boundary qualifies;
- result exactly 42 days old is excluded;
- result at the same start instant as current Activity is excluded as not prior;
- highest raw average wins;
- rounded-display ties do not override a raw-value winner;
- exact raw tie chooses earliest Activity then stable Activity ID.

### Eligibility

- current eligible trusted Virtual Ride gets context;
- outdoor Ride with its own best-20 does not gain trusted context;
- non-cycling Activity does not gain trusted context;
- current stale/pending Performance result yields unavailable/rebuild-needed context;
- prior stale/ineligible/outdoor/non-virtual results do not enter baseline;
- CSV/source-summary watts never enter baseline;
- timezone-unknown prior result cannot enter exact timed window;
- no eligible prior result yields Unavailable rather than zero/fallback.

### Activity Review UI

- eligible rich FIT review shows a clearly labeled **Compared with previous 6 weeks** block;
- This ride + Prior 42-day best are visually prominent;
- neutral watt difference is shown when a prior baseline exists;
- prior baseline has an explicit Open prior ride link/action to its stable Activity;
- View Performance link is present;
- unavailable baseline is clear and compact;
- no green/red evaluative semantics are introduced;
- provenance details include policy/method/window/current-exclusion context;
- thin reviews remain thin and do not fabricate context.

### Regression / data access

- accepted P1/P2-01/P2-02/P2-03 tests remain passing;
- comparison rendering reads persisted Performance metadata/results and does not trigger archive import, source re-extraction, or `rebuild-performance`;
- no native record scan is needed merely to select the prior baseline;
- loopback-only server behavior remains unchanged.

Use synthetic fixtures only in automated tests.

## 17. Independent verification

Create a privacy-safe verifier for the full local history that independently computes each eligible Activity's prior baseline from persisted trusted P2-03 results.

The verifier must not call the production recent-context selector as its oracle.

For every eligible current result with absolute time:

- form the exact prior interval `(t - 42 days, t)`;
- independently filter prior eligible P2-03 results;
- select max raw watts with accepted deterministic ties;
- compare production baseline Activity/result identity and raw/display values;
- confirm current Activity exclusion;
- confirm unavailable cases.

Also verify zero baselines from outdoor/non-eligible results.

This verifier should operate on persisted performance results/metadata, not source archives/native streams.

## 21. Acceptance criteria

P2-04 is ready for Analyst acceptance only when:

1. eligible Activity Review can show current best-20 against prior 42-day trusted best;
2. prior interval is exactly `(t - 42 days, t)`;
3. current Activity is excluded from its own baseline;
4. only current eligible P2-03 results under the same policy/method/duration may participate;
5. highest raw prior best wins with deterministic ties;
6. no-baseline cases show Unavailable;
7. stale/missing trusted history does not silently fall back to other evidence;
8. comparison is neutral and explainable;
9. prior contributing Activity is openable;
10. Activity Review links to Performance;
11. provenance/method/window basis is inspectable;
12. existing rich FIT and thin review behavior remains accepted;
13. selection uses persisted Performance history and does not re-import/reparse the historical archive;
14. Activity Review does not automatically trigger `rebuild-performance`;
15. independent full-history baseline verification agrees with production;
16. all automated tests pass;
17. full-history restart/browser acceptance passes;
18. Owner approves visual/usability;
19. verification publication respects privacy boundary;
20. Analyst accepts P2-04 at Gate 2.

## 22. Stop-and-report conditions

Stop and report if:

- P2-03 persisted history cannot support the comparison without reading/recalculating native streams for ordinary page rendering;
- the current/prior eligibility policy would need to diverge from accepted P2-03;
- a material number of eligible results lack absolute times needed for the exact 42-day window;
- a new source-ranking or canonicalization decision is required;
- comparison semantics conflict materially with accepted P2-03 rolling-window behavior;
- implementation requires rebuilding from the historical archive;
- implementation begins expanding into P2-05 sync, training state, outdoor estimated power or Phase 3.

Ordinary no-baseline cases are expected and are not a stop condition.
