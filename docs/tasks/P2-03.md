# P2-03 — Trusted 20-Minute Performance History

**Status:** Analyst-authored JIT; implementation not started  
**Phase:** Phase 2 — Historical context and performance history  
**Task:** P2-03  
**Controlling product:** RideWorks

## 1. Purpose

Build the first trustworthy longitudinal performance view in RideWorks.

P2-03 must derive and persist 20-minute-power history from the rider's imported history using the already accepted `best-average-power-v1` complete-window semantics, but only for the conservative Phase 2 trusted cohort:

- cycling Virtual Ride evidence;
- native source power;
- a complete eligible native 20-minute window;
- no outdoor Ride power;
- no CSV/source-summary watts substituted for native streams;
- no resampling, interpolation or repair.

The rider should be able to open a real **Performance** page, see chronological trusted 20-minute-power history, inspect what qualifies, and open the contributing Activity.

P2-03 does **not** add the prior-six-week comparison to Activity Review; that is P2-04.

## 4. Settled trusted-cohort policy

The following are explicit product decisions and are not open implementation choices.

### 4.1 Outdoor Ride power is excluded

An activity classified as outdoor/`Ride` must not contribute to the trusted Phase 2 20-minute trend even if a native source contains power.

The reason is evidence quality: Owner considers historical outdoor power suspect and the archive research established that a numeric power stream does not prove measured provenance.

Outdoor power remains preserved source evidence. P2-03 must not delete, alter or relabel it.

### 4.2 Virtual Ride native power is accepted for this purpose

A Virtual Ride may contribute when a native source stream satisfies the accepted complete-window rules.

Do not label this power `measured` merely because the activity is virtual or because native power exists. The narrower claim is:

> this native Virtual Ride power is eligible for the Phase 2 trusted 20-minute history.

### 4.3 No summary substitution

The following must never satisfy P2-03's native-power requirement:

- Strava CSV average watts;
- FIT/TCX session/lap average power;
- weighted/normalized power;
- any summary maximum;
- later estimated outdoor power;
- a fabricated zero/missing stream.

## 5. Virtual Ride classification for this analysis

Classification is purpose-specific and retains provenance.

Use this conservative policy:

1. If Strava-export activity-type evidence exists, use the latest non-empty imported Strava activity-type observation for this classification and retain its Source ID in the derived-result context.
2. A latest Strava type of `Virtual Ride` qualifies the activity-type gate.
3. A latest Strava type of `Ride`, Run, Walk, Rowing or another non-virtual type does not qualify, regardless of power presence.
4. If no Strava activity-type observation exists, an unambiguous native session classification such as FIT `sub_sport=virtual_activity` may satisfy the Virtual Ride gate.
5. If available source evidence materially conflicts about whether the activity is virtual versus outdoor and the conflict cannot be resolved by the policy above, exclude it with an explicit ambiguity reason rather than guessing.

This is not a universal canonical activity-type policy.

## 6. Native source candidates

P2-03 may use native records from the production file formats imported by P2-01:

- FIT;
- TCX;
- GPX;

provided the current extraction supplies native timestamp/power records compatible with the accepted calculation.

Do not restrict the longitudinal implementation to FIT merely because Phase 1's first ride was FIT.

For each Virtual Ride candidate:

1. identify current file-source extractions with native records/power;
2. evaluate the accepted best-20 method independently for each candidate source;
3. if exactly one native source produces an eligible result, that source may support the trusted Activity result;
4. if more than one distinct current native source produces an eligible result, exclude the Activity as ambiguous rather than selecting the highest result;
5. if no source produces an eligible result, retain an explicit ineligible/unavailable status/reason.

An ineligible competing source does not by itself invalidate one unambiguous eligible source.

Do not introduce a global source ranking.

## 7. Best-20 calculation semantics

Reuse **exactly** the accepted `best-average-power-v1` semantics:

- exactly 1,200 consecutive source records;
- timestamps `t` through `t+1199`;
- half-open interval `[t, t+1200)`;
- every adjacent timestamp delta exactly one second;
- all 1,200 power values non-null;
- legitimate zero watts count;
- missing power invalidates the candidate window;
- no resampling;
- no interpolation;
- no smoothing;
- no gap repair;
- no timestamp repair;
- no deduplication;
- evaluate every eligible window;
- highest raw average wins;
- exact tie chooses earliest window;
- retain unrounded average;
- display nearest whole watt using the accepted .5-up behavior.

The existing production calculation may be refactored so it works on any supported native record extraction rather than FIT-only wording/context, but its mathematical semantics must not change.

Unknown/naive native timestamps do not establish the absolute one-second timing required by this trusted history and must not be guessed into eligibility.

## 8. Durable analytical history

P2-03 must persist the longitudinal result/status because it will be repeatedly consumed.

Use the simplest specific representation appropriate to this private application.

For each evaluated Activity, retain or be able to reproduce at least:

- RideWorks Activity ID;
- eligibility/status;
- explicit ineligibility/unavailability reason when not eligible;
- cohort/eligibility-policy version;
- duration seconds (1,200 now; representation must not inherently prevent later durations);
- calculation method/version (`best-average-power-v1`);
- selected native Source ID when eligible;
- selected extraction ID when eligible;
- activity-type/classification evidence identity used for the decision where applicable;
- raw unrounded average watts when eligible;
- displayed rounded watts;
- best-window start/end/source-record context;
- calculation/rebuild timestamp.

Do not copy native streams into the derived-result table.

The representation may be a specific best-power/performance table rather than a generalized metrics framework.

### 8.1 Versioning and stale evidence

Derived history must never silently survive a changed input as though still current.

At minimum:

- an eligible result is tied to the exact source/extraction used;
- if that extraction is replaced/re-extracted, the old result must no longer appear as current trusted history;
- if the activity classification used for eligibility changes, a stale result must not continue to plot silently;
- rebuilding must be safe and reproducible from current preserved sources.

Implementation may use foreign keys, input identities, current-result checks or a small generation mechanism.

Do not build a generic dependency graph.

## 9. Rebuild workflow

Add one explicit command that builds/rebuilds trusted performance history from the current RideWorks store.

Preferred shape:

```bash
python -m rideworks --data-dir <data-dir> rebuild-performance
```

A similarly clear name is acceptable.

The rebuild must:

- evaluate the full Activity population;
- avoid loading native streams for obviously excluded outdoor/non-virtual Activities;
- calculate current eligible Virtual Ride sources;
- persist current statuses/results;
- emit a privacy-safe aggregate report including evaluated count, Virtual Ride candidates, eligible count, and ineligible counts by reason;
- retain the previously accepted history if a fatal rebuild failure occurs before a complete replacement can be committed.

A normal ineligible Activity is not a fatal rebuild error.

Unexpected source corruption/invariant failures must not be silently converted into a normal low-quality result.

P2-03 does not require automatic background rebuilding.

P2-05 may later arrange recalculation when new synced Activities arrive.

## 10. Performance read boundary

Add a narrow production read boundary for the current trusted performance history.

It must provide the UI with only the metadata/results needed for the longitudinal view, such as:

- Activity ID;
- preferred display title under the accepted P2-02 presentation policy;
- supported activity date/time evidence;
- eligibility/status/reason;
- raw/display watts when eligible;
- selected source/extraction/method/policy context needed for inspectability.

Do not load native record streams merely to render the Performance page.

Do not expose an old stale result as current when its input identities no longer match.

### 11.1 Page content

The first Performance page should contain:

- heading: **Performance**;
- a clear **20-minute power history** section;
- a compact statement of the trusted cohort, e.g. Virtual Ride native power only;
- chronological chart containing every current eligible historical result;
- date, title and best-20 watts available when inspecting a point;
- an interaction that opens the contributing Activity;
- a small inspectable explanation of eligibility/method/provenance;
- a useful empty state if no trusted history has yet been rebuilt or no Activity qualifies.

No outdoor points may appear as zero, gray placeholders or estimated values.

### 11.2 Chart semantics

The chart must:

- render all eligible current results rather than an arbitrary recent subset;
- order by supported activity date/time;
- use the stored raw result for ordering/comparison and the accepted whole-watt value for normal display;
- show a clearly labeled watt axis;
- avoid smoothing/interpolation that implies calculated intermediate performance;
- not fabricate a continuous daily performance series.

A line connecting observed points is acceptable if the UI remains clear that points are observed eligible ride results rather than daily estimates.

If the y-axis is truncated rather than starting at zero, its numeric scale must be visibly explicit; do not visually exaggerate small changes through an unlabeled axis.

The exact SVG dimensions/ticks/point styling are implementation discretion.

### 11.3 Point interaction

At minimum:

- pointer/hover inspection;
- keyboard inspection comparable to the accepted ride chart where practical;
- selected point readout with local/display date, source title and watts;
- click/open affordance to `/activities/<activity_id>`.

Do not put native stream data in the Performance page payload.

## 12. Date/time presentation

Follow the accepted P2-02 policy.

- Known absolute Activity instants display in browser-local time.
- Timezone-unknown source dates remain source dates and remain explicitly unknown.
- Do not rewrite persisted source timestamps.
- Do not invent a timezone merely to place an otherwise unsupported date on the chart.

If an eligible best-20 calculation lacks any defensible longitudinal Activity date, retain the derived result/status but do not silently plot it at an invented date; report the missing-date condition explicitly.

## 13. Eligibility/provenance explanation

The Performance page must make the trust rule discoverable without overwhelming the chart.

A compact details panel is sufficient. It should explain:

- Virtual Ride native source power is the initial trusted cohort;
- outdoor Ride power is intentionally excluded as suspect;
- presence of native power is not labeled measured by default;
- complete 1,200-sample one-Hz windows are required;
- no interpolation/repair occurs;
- method/version is `best-average-power-v1`;
- ineligible/missing Activities are not plotted as zero.

Do not claim the cohort is physiologically perfect or universally authoritative.

## 19A. Owner-directed Performance experience correction

Gate 1 Owner review found that the initial 1,022-point scatter is analytically honest but not a practical primary Performance experience.

The accepted direction for P2-03 is now:

### 19A.1 Performance modes

The Performance page must provide three rider-oriented modes:

- **Current** — answer “What have I demonstrated recently?”
- **Trend** — answer “How is demonstrated 20-minute capability changing?”
- **History** — answer “Where have my strongest periods/results been?”

`Trend` is the default mode.

This is one Performance capability, not three separate pages or architectural subsystems.

### 19A.2 Trend view

The primary Trend visualization must not present all eligible ride results as equally important observations.

Instead:

- show a **rolling 42-day demonstrated-best 20-minute power** line as the primary signal;
- eligible ride-level best-20 results may remain available as subdued supporting dots/evidence;
- provide a simple control to choose **Trend only** versus **Trend + rides**;
- do not connect individual ride results into a ride-to-ride line;
- do not use generic statistical smoothing or averages across easy/hard rides;
- make clear that the line represents the best qualifying result demonstrated within the rolling 42-day window, not an estimate for every day.

A step-like line is appropriate when the rolling best changes discretely.

### 19A.3 Time-range controls

Provide compact practical ranges for Trend/History exploration:

- 3 months;
- 6 months;
- 1 year;
- 3 years;
- All.

Default to **1 year** unless the real UI demonstrates a clearly better default during Owner review.

Do not add a generalized date-query builder in P2-03.

### 19A.4 Summary cards

Provide compact summary values that make the page useful without interpreting the entire chart.

The initial set should include:

- **Current 42-day best**;
- **Latest eligible ride**;
- **Best in last 12 months**;
- **Lifetime best**.

Each result should show watts and enough date/activity context to open or understand the contributing ride.

These values are derived from the already accepted trusted cohort/results; they must not introduce a different eligibility rule.

### 19A.5 Current mode

Current should emphasize the rider’s present demonstrated evidence, not a dense long-term plot.

At minimum surface:

- current rolling 42-day best;
- date/contributing Activity;
- age/freshness of that evidence;
- latest eligible ride result.

A large chart is optional in Current if the summary is more useful without one.

Do not add P2-04’s current-ride-versus-prior-six-week comparison here.

### 19A.6 History mode

History should make long-term peaks practical to inspect rather than defaulting to 1,022 equal-weight dots.

At minimum it should support the selected time range and make lifetime/period best results easy to find.

Annual/seasonal peak presentation is allowed if simple and clearly derived from the same trusted results, but do not build a separate records subsystem or arbitrary-duration power curve.

The complete eligible ride-level history remains inspectable as supporting evidence.

### 19A.7 Selected result interaction

The selected/readout result should default to the most recent meaningful result for the active view, not the oldest observation.

The readout should expose:

- browser-local date/time where known;
- preferred source title;
- displayed best-20 watts;
- stable link/open action to the contributing Activity.

### 19A.8 Visual direction

Use the Owner-approved conceptual direction from the Performance redesign discussion:

- compact Current / Trend / History tabs;
- restrained range and evidence controls;
- small summary cards above the chart;
- rolling 42-day-best line visually dominant;
- eligible ride dots visually secondary when enabled;
- concise selected-result readout;
- compact Eligibility & method panel.

The generated concept image is a **design-direction reference**, not a pixel-perfect specification. Exact spacing, icons, chart dimensions and card wording remain implementation discretion.

### 19A.9 Scope boundary

This correction remains inside P2-03 because it changes how the already-built trusted 20-minute history is made usable.

P2-03 still must **not** implement:

- the P2-04 Activity Review comparison against the prior 42-day best;
- training-state interpretation;
- FTP/Wkg/power-curve features;
- outdoor power eligibility;
- predictions or AI interpretation.

## 22. Stop-and-report conditions

Stop and report if:

- the real 1,264 Virtual Ride population contains a material power/type/source category not covered by the trusted-cohort policy;
- a large portion of apparently normal Virtual Ride native power becomes ineligible for a reason that suggests the accepted one-Hz method is not appropriate for historical data;
- XML/native power representation cannot support the accepted method without repair/resampling;
- source selection requires choosing among multiple eligible competing Sources at material scale;
- the real archive shows material conflicts between Strava Virtual Ride classification and native source classification;
- durable result invalidation would require a generalized dependency system rather than a small specific solution;
- the Performance chart cannot make all eligible points available without materially misleading aggregation;
- implementation begins expanding into P2-04 six-week context, outdoor estimated power, training-state metrics, API sync or Phase 3.

Ordinary Activities that are too short, have gaps, lack power, or lack a complete 20-minute window are expected ineligible cases and do not require a design stop by themselves.
