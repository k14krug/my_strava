# P2-01 — Historical Strava-Export Import and Enrichment

**Status:** Analyst-authored JIT; implementation not started  
**Phase:** Phase 2 — Historical context and performance history  
**Task:** P2-01  
**Controlling product:** RideWorks

## 1. Purpose

Import the rider's known Strava bulk-export activity history into RideWorks through one durable, idempotent workflow.

P2-01 must turn the researched export population into real RideWorks Activities + Sources while preserving source evidence, actual activity titles, referenced FIT/TCX/GPX artifacts, CSV-only activities, and conservative association semantics.

This is the history foundation for the later Phase 2 Activities browser and trusted performance-history work.

P2-01 does **not** build the scalable browser, historical 20-minute trend, six-week comparison, or Strava API sync. Those are P2-02 through P2-05.

## 5. Required user-facing workflow

Add one documented command for bulk historical import.

Preferred shape:

```bash
python -m rideworks --data-dir <data-dir> import-strava-export <export.zip-or-root>
```

Supporting both the original ZIP and an already-extracted export root is acceptable if simple.

If supporting the ZIP directly creates disproportionate complexity, an extracted-root input is acceptable only after stopping for Analyst review because direct ZIP use is the preferred rider workflow.

The rider must not manually import 1,421 files.

## 6. Existing-store compatibility

P2-01 extends the accepted Phase 1 store. It must not require throwing away an existing RideWorks data directory.

A minimal schema/version migration is authorized if needed.

Requirements:

- opening a valid Phase 1 schema-1 store must migrate safely to the P2-01 representation;
- migration must preserve existing Activity/Source IDs, original artifacts, current extraction evidence, and P1-01/P1-03 behavior;
- failed migration must not leave a falsely usable partially migrated store;
- no ORM or general migration framework is required;
- the simplest explicit SQLite migration appropriate to this private app is preferred.

Do not redesign storage merely because P2-01 introduces more source kinds/formats.

## 7. Strava export evidence model

### 7.1 CSV source evidence

Every CSV row is source evidence for one historical Strava activity.

Retain enough row-level information to support later use, including at minimum where present:

- Strava activity ID;
- activity name/title;
- activity date/start evidence;
- activity type and sport type;
- filename/reference;
- distance/duration/elevation summary fields needed by later browser display;
- useful source summary power/HR/cadence fields as source values, without treating them as substitutes for native streams;
- trainer/commute/private or other low-cost structured fields only where they are actually useful and their semantics are understood.

Do not persist arbitrary free-text/export columns merely because they exist.

Do not turn imported CSV values into provenance-free Activity columns.

### 7.2 CSV snapshot preservation

Preserve the exact `activities.csv` bytes, or an equivalent exact source snapshot, once per imported export so the row extraction can be reproduced.

Do not create 1,434 redundant copies of the same CSV file.

Each per-Activity Strava-export source/observation must retain enough identity to trace back to its row in that preserved snapshot.

### 7.3 Source titles

The Strava `Activity Name` is actual source title evidence.

Expose it through the Store read boundary with Strava-export provenance.

Do not overwrite or delete the Phase 1 derived title concept. Presentation preference belongs to later UI/source-selection policy.

## 8. Referenced file artifacts

For every referenced activity file:

- read the exact member/file bytes;
- identify packaging/content format from actual content, not suffix alone;
- preserve the exact artifact unchanged in RideWorks-managed storage;
- retain SHA-256 and byte size;
- associate it to the Activity identified by the explicit Strava CSV file relationship;
- extract only understood typed evidence;
- retain parser/extraction versioning;
- preserve native sample order/timing where streams are extracted.

Artifact hashes identify exact artifacts, not Activities.

If the exact artifact already exists in RideWorks from P1-01, reuse/associate the established evidence rather than copying it or creating a duplicate Activity.

## 9. Format envelope

Production import must support the known export formats:

- FIT / FIT.GZ;
- TCX / TCX.GZ;
- GPX / GPX.GZ.

### FIT

Reuse the accepted production FIT decoding/extraction path wherever applicable.

Do not fork a second incompatible FIT interpretation for bulk import.

### TCX / GPX

A small production parser using standard-library XML facilities is acceptable and preferred if sufficient.

Extract only understood fields needed for durable evidence and later Phase 2 work.

At minimum, where present and semantically clear:

- timestamps;
- power;
- heart rate;
- activity/session-level timing/distance summary evidence useful for later display;
- basic sport/type context when supplied.

Cadence/elevation/speed may be retained when straightforward and useful, but do not expand P2-01 into exhaustive XML schema support.

Unknown/private extension fields need not be normalized. The preserved original remains the recovery path.

Do not silently normalize irregular source timing.

### Compression

Gzip members/artifacts must preserve the received compressed bytes unchanged as the original artifact.

Parsing may decompress transiently.

## 10. Activity association rules

Use the strongest available evidence; do not invent a generalized fuzzy reconciler.

### New export activities

For a CSV row not already represented in RideWorks:

- create one application-owned Activity;
- attach the Strava-export row source;
- attach the explicitly referenced file source when one exists.

### Phase 1 representative enrichment

The local acceptance run must begin with the Phase 1 representative FIT already imported.

When the export is then imported:

- the exact matching artifact must resolve to the existing Source/Activity;
- the Strava-export row source must enrich that same Activity;
- the Activity count must remain 1,434, not 1,435;
- the existing RideWorks Activity ID must remain unchanged;
- the actual Strava source title must become available as source evidence.

### Other pre-existing activities

Exact established artifact identity plus explicit export relationship is sufficient association evidence.

Strava external ID already attached to an Activity is sufficient for subsequent same-source enrichment.

Do not implement broad time/distance/name fuzzy matching in P2-01.

If a pre-existing Activity appears to match only through ambiguous heuristics, leave it unresolved and report it.

## 11. CSV-only activities

For each of the 13 known no-file rows:

- create/retain a normal RideWorks Activity;
- attach Strava-export source evidence;
- do not create a fake file Source;
- do not create empty native streams and call them observed absent;
- detailed stream availability remains unknown/unavailable from that source.

These activities must still be listable through the Store read boundary for P2-02.

## 12. Read boundary required for P2-02/P2-03

Extend the Store with a simple source-aware activity-history read boundary.

P2-01 does not need the final browser query API, but later tasks must be able to retrieve, without reading research-report files:

- Activity ID;
- available source title(s) and provenance;
- source type/activity-type evidence;
- source date/start evidence;
- useful summary evidence and missingness;
- associated source kinds/formats;
- whether a native power stream exists;
- current extraction/source identity needed for later best-20 derivation.

Do not encode a universal canonical-source ranking in this API.

A narrow preferred-title helper is acceptable only if it clearly expresses a presentation policy rather than mutating source evidence.

## 13. Idempotency

Re-importing the same export after restart must be idempotent.

At minimum:

- no duplicate Activity for the same established Strava activity;
- no duplicate equivalent Strava-export row source;
- no duplicate exact file Source/artifact;
- existing Activity/Source IDs remain stable;
- changed source bytes or materially changed CSV row evidence are not silently treated as identical.

P2-01 does not need a generalized multi-version export-history UI. Preserve enough source/version identity to avoid destructive overwrite.

## 14. Failure behavior

The bulk workflow should continue past an independent bad activity/file when safe.

At completion, provide a compact import report including:

- CSV rows seen;
- Activities created;
- existing Activities enriched/reused;
- CSV-only activities;
- referenced artifacts attempted;
- artifacts imported/reused;
- format counts;
- failures/unresolved associations.

A failed file import must not expose a completed false Source/extraction.

Do not roll back 1,400 successful independent activities solely because one later file is bad.

Structural export failures that make row/file identity unreliable should fail the bulk operation clearly before destructive work where practical, for example:

- missing/unreadable `activities.csv`;
- required identity/reference columns unavailable;
- duplicate/ambiguous Strava activity IDs that violate the known export model;
- unsafe archive member/path traversal;
- malformed ZIP/container preventing reliable access.

## 16A. Analyst-authorized handling for non-absolute FIT lap timestamps

The real-export acceptance run found seven otherwise valid FIT activities where `fitdecode==0.11.0` returns an integer for `lap.timestamp`, while all native record timestamps in those activities decode as aware absolute datetimes.

This evidence does **not** establish what clock/timebase the integer represents. P2-01 is therefore authorized to handle this narrow case losslessly as follows:

- if a FIT `lap.timestamp` decodes as an aware datetime, keep the accepted Phase 1 behavior and persist its normalized UTC ISO representation;
- if a FIT `lap.timestamp` decodes as an integer, do **not** convert or guess it into UTC;
- persist the exact integer as explicit typed source evidence tied to that lap/source order and field name;
- mark its interpretation/status explicitly as present but uninterpreted/non-absolute, rather than missing;
- leave the lap's absolute timestamp representation unavailable/null for that field;
- do not replace it from neighboring record timestamps, session timing, lap start time, elapsed/timer duration, CSV metadata, or any inferred value;
- re-extraction must reproduce the same raw integer evidence from the preserved original.

The physical representation is implementation discretion. A small FIT-specific context structure/table or an explicit typed lap field is acceptable. Do **not** introduce a generalized EAV/provenance framework solely for this case.

This authorization does not weaken the accepted Phase 1 record-timing contract:

- non-absolute FIT **record** timestamps remain unsupported and must not enter native stream analysis;
- session/event timestamps and other FIT timing fields retain their existing strict behavior unless separately reviewed;
- the P1-02 `best-average-power-v1` analysis continues to use absolute native record timestamps only;
- no integer FIT timestamp may be labeled UTC or device-relative without source evidence establishing that interpretation.

If the continued full-export run encounters a non-absolute FIT timestamp in a different message/field, stop and report that new evidence rather than silently extending this policy.

## 17. Automated tests

Add focused privacy-safe tests covering at least:

### Migration/regression

- Phase 1 schema/store migrates and remains readable;
- existing FIT import/re-extraction/Activity Review tests continue to pass.

### CSV/export handling

- CSV row source persists with external ID/title/type/date and provenance;
- exact CSV snapshot is preserved once;
- duplicate import is idempotent;
- CSV-only activity remains valid without fake streams;
- irrelevant free-text is not accidentally promoted into required structured evidence.

### Association

- CSV row + explicit filename associate to one Activity;
- existing exact FIT artifact is enriched rather than duplicated;
- ambiguous pre-existing match is not force-merged.

### File formats

- FIT path reuses accepted production behavior;
- TCX and GPX minimal fixtures import expected timestamp/power/HR evidence;
- gzip variants preserve exact compressed originals;
- missing/irregular timestamps are preserved rather than repaired;
- malformed individual source reports failure without corrupting unrelated imports.

### Safety

- invalid ZIP/export structure fails clearly;
- path traversal/member escape is rejected;
- failed source parse leaves no completed false source/extraction;
- no source-summary watts are promoted into native record power.

## 21. Stop-and-report conditions

Stop and report if:

- the real export materially differs from the established 1,434/1,421/13 population;
- direct ZIP support proves materially complex and switching to extracted-root-only would change the agreed rider workflow;
- importing TCX/GPX requires a broad parser dependency/framework rather than a small understood implementation;
- known files cannot be parsed without silently normalizing important timing/evidence;
- the Phase 1 representative cannot be confidently associated with its explicit export row/source;
- safe schema migration would require destructive replacement of the accepted store;
- activity reconciliation appears to require fuzzy heuristics beyond exact artifact/external identity/explicit export relationships;
- preserving exact originals conflicts with the proposed bulk workflow;
- a privacy-safe verification report cannot be produced;
- implementation starts expanding into performance history, outdoor power interpretation, API synchronization, or Phase 3.

Ordinary malformed individual activity files should be reported by the bulk importer rather than triggering a design stop unless they expose a new policy question.
