# P1-02 — Single-Ride Analysis Core

**Status:** Analyst-authored JIT; implementation not started  
**Phase:** Phase 1 — Useful single-ride review  
**Task:** P1-02  
**Controlling product:** RideWorks

## 1. Purpose

Implement the narrow RideWorks analysis layer required by the Phase 1 activity-review experience.

P1-02 consumes the durable P1-01 Activity/Source/current-extraction read boundary and produces a trustworthy Phase 1 analysis package containing:

- the FIT-backed source summary required by Phase 1;
- the native ordered power and heart-rate streams already preserved by P1-01;
- one application-derived metric: best 20-minute average power;
- explicit derivation/source/extraction context sufficient to reproduce and explain that result.

This task is deliberately small. Its job is to make P1-03 straightforward, not to build a general cycling analytics engine.

P1-02 does **not** build the browser UI. It does not add zones, normalized-power-style metrics, training load, interval detection, general power-duration curves, historical comparison, training-state analysis, or planning.

## 2. Background / question being answered

P1-01 established the durable evidence boundary:

- application-owned Activity and Source identities;
- exact original preservation;
- typed FIT session summary;
- ordered native timestamp/power/HR records;
- explicit signal availability and missingness;
- current extraction identity;
- a callable read API usable by P1-02.

The Phase 1 acceptance contract now requires the first application analysis derived from that evidence: best 20-minute power for the representative ride.

The implementation question is:

> What is the smallest transparent analysis boundary that gives P1-03 trustworthy source-backed ride data and a reproducible best-20-minute result without prematurely designing the later analytics architecture?

The answer for this task is intentionally simple: consume the current P1-01 extraction, preserve its native evidence unchanged, calculate best 20-minute power on demand with explicit method/version/input context, and expose the result through a small callable RideWorks interface.

## 8. Required implementation

### 8.1 Analysis boundary

Provide a small callable RideWorks analysis interface, approximately:

```python
analyze_activity(activity_id)
```

Exact naming is implementation discretion.

The returned Phase 1 analysis package must make the following categories distinguishable:

- Activity identity;
- selected FIT Source identity;
- current extraction identity/version;
- source-backed FIT summary;
- native ordered power/HR records or stream representation derived directly from those records without resampling;
- signal availability;
- application-derived best 20-minute power;
- derivation method/version and eligibility/result details.

Do not flatten source summary values and application derivations into one provenance-free summary dictionary where their origins become ambiguous.

### 8.2 Source selection boundary

For P1-02, analyze the single FIT Source established for the Phase 1 Activity.

Do not create a general source-ranking rule.

If the requested Activity has no usable current FIT Source, return/fail clearly.

If an Activity presents multiple candidate Sources such that choosing one requires evidence-selection policy, stop/fail clearly rather than silently ranking them. Multi-source analytical selection belongs later.

### 8.3 Source-backed summary

Expose the P1-01 FIT session summary values required by Phase 1 unchanged in meaning:

- start/date-time evidence available from FIT;
- sport;
- sub-sport;
- total elapsed duration;
- total timer duration;
- distance;
- total ascent when present;
- average power;
- maximum power;
- average heart rate;
- maximum heart rate;
- average cadence.

These remain FIT Source evidence.

Do not recalculate them from the stream and overwrite them.

Do not substitute zero for missing source summary fields.

P1-02 may add presentation-neutral labels/metadata that let P1-03 know these values are source-supplied, but actual display formatting belongs to P1-03.

### 8.4 Native power/HR stream exposure

Expose ordered native records needed by the Phase 1 chart:

- record index/order;
- timestamp;
- power;
- heart rate.

Preserve:

- original record order;
- original timestamps;
- legitimate zero power;
- missing values.

Do not:

- resample to one-second data;
- smooth;
- interpolate;
- remove records with missing values;
- deduplicate timestamps;
- manufacture chart points.

The representative ride happens to be complete one-second data. That is an observed property to verify, not a transformation policy.

### 8.5 Best 20-minute power semantics

Implement exactly this narrow Phase 1 definition.

#### Candidate window

A valid 20-minute candidate contains exactly **1,200 consecutive source records**.

For a candidate beginning at record timestamp `t`:

- the 1,200 record timestamps must be exactly `t, t+1s, ..., t+1199s`;
- equivalently, the window is the half-open time interval `[t, t+1200s)`;
- all 1,199 adjacent timestamp deltas inside the window must be exactly one second;
- every one of the 1,200 records must contain a power value.

This convention intentionally treats a one-Hz power stream as 1,200 sample slots covering 1,200 seconds. Do not require 1,201 endpoint samples.

#### Power values

- legitimate zero watts are included in the average;
- missing power is not zero;
- a candidate containing any missing power is ineligible;
- negative or otherwise impossible power handling is not a new P1-02 policy: preserve the P1-01 decoded value and stop/report if the representative data reveals an unexpected condition that makes the calculation semantically questionable.

#### Search

Evaluate every eligible 1,200-record window in source-record order.

For each eligible window:

```text
average_watts = sum(power values) / 1200
```

The best result is the eligible window with the highest unrounded average.

If multiple windows have the same best unrounded average, choose the earliest window by source-record order.

Do not use FIT session average power, Strava values, or any vendor best-effort value as the calculation input.

#### Result context

Return enough information to reproduce/inspect the result, including at minimum:

- Activity ID;
- Source ID;
- extraction ID;
- analysis method/version;
- duration: 1,200 seconds;
- start record index;
- end-exclusive record index;
- start timestamp;
- end-exclusive timestamp;
- number of samples: 1,200;
- unrounded average watts;
- rounded Phase 1 presentation watts;
- eligibility/status.

A reasonable initial method identifier is `best-average-power-v1` or equivalent. It must be explicit and change if the calculation semantics materially change.

#### Rounding

Retain the unrounded result for calculation/verification context.

For Phase 1 presentation, provide a whole-watt value rounded to nearest watt with .5 rounding upward.

Do not round individual samples before averaging.

### 8.6 Unavailable/ineligible behavior

If the activity contains no eligible complete 1,200-record power window, return an explicit unavailable/ineligible result rather than:

- interpolating;
- filling missing power with zero;
- shortening the duration;
- using session average power;
- returning a misleading zero.

The reason should be inspectable at a useful level, for example:

- activity shorter than required;
- no complete timestamp-contiguous window;
- no complete power window.

Do not build a generalized diagnostics taxonomy.

### 8.7 Persistence decision for P1-02

Do **not** add durable analytical-result persistence merely because best-20-minute power may eventually be useful longitudinally.

For Phase 1, calculate it on demand from the current extraction and return explicit Source/extraction/method context.

This is an intentional narrow implementation choice, not a permanent decision that all future derived metrics should be query-time calculations.

Benefits for this slice:

- no stale-result invalidation mechanism is needed;
- re-extraction naturally causes the next calculation to use the new current extraction;
- provenance stays explicit;
- P1-03 receives exactly what it needs;
- DATA-004 remains open for later durable analytical history when longitudinal use makes persistence worthwhile.

### 8.8 Re-extraction behavior

The analysis result must identify the extraction it used.

After P1-01 re-extraction changes the Source's current extraction identity, a new P1-02 analysis call must:

- consume the new current extraction;
- report the new extraction ID;
- recalculate best 20-minute power from that extraction.

Do not cache a result in a way that can silently survive input revision without invalidation.

### 8.9 Minimal CLI / verification access

Add only the smallest CLI/debug surface useful for verification and P1-03 development if one is helpful.

An example would be:

```bash
python -m rideworks analyze <activity-id>
```

If added, output should be compact and privacy-conscious:

- identities/version context;
- source summary;
- stream counts/availability;
- best-20-minute result metadata.

Do not dump the full raw power/HR stream to normal CLI output.

A new CLI command is optional if the callable API plus verification utility provides a cleaner boundary.

## 10. Verification / test procedure

### 10.1 Automated tests

Use privacy-safe synthetic data / the existing synthetic FIT fixture and temporary data directories.

Tests must cover at least:

#### Evidence boundary

- source FIT summary is exposed as source evidence, not relabeled as calculated;
- source elapsed and timer durations remain distinct;
- missing source-summary values remain missing;
- native record order/timestamps/power/HR remain unchanged;
- zero power remains zero;
- missing power/HR remain missing;
- result identifies the current Source and extraction.

#### Best-20-minute calculation

- exactly 1,200 consecutive one-second samples form one valid 20-minute window;
- 1,199 samples are insufficient;
- 1,201+ samples produce sliding candidates;
- legitimate zero-power samples are included;
- a missing-power sample invalidates only candidate windows containing it;
- a one-second timestamp gap invalidates windows spanning the gap;
- duplicate/backward timestamps invalidate windows spanning that timing defect;
- another complete 1,200-sample window elsewhere may still be eligible;
- tie on unrounded average selects the earliest source-record window;
- unrounded result and rounded-whole-watt result follow the declared semantics;
- no eligible window returns explicit unavailable/ineligible state.

Use simple synthetic sequences whose expected result can be reasoned about directly. Do not use the production helper as the test oracle for all expected values.

#### Extraction revision

- analysis reports the current extraction ID;
- after successful P1-01 re-extraction, analysis reports the new extraction ID and recalculates from current evidence.

### 10.2 Independent verification

Provide a separately expressed verification calculation for best 20-minute power.

It must not call the production rolling/best-window helper.

For the representative ride, independently:

1. retrieve ordered current-extraction timestamp/power records;
2. enumerate candidate start positions;
3. verify each 1,200-record candidate has exact one-second timestamps and complete power;
4. directly sum its 1,200 power samples;
5. select the highest mean, earliest on ties.

Compare the independent result with production analysis.

Required tolerance:

- unrounded average-power difference: **<= 0.01 W**;
- rounded whole-watt result: exact match;
- selected start record index: exact match.

If these do not agree, P1-02 is not ready for review.

### 10.3 Representative local-data acceptance

Run P1-02 against the representative local-only FIT through a disposable RideWorks store.

The procedure should:

1. import a disposable copy through the accepted P1-01 importer;
2. obtain the RideWorks Activity ID;
3. run the P1-02 analysis boundary;
4. confirm one FIT Source/current extraction is being analyzed;
5. confirm the required FIT source summary remains available;
6. confirm the analysis sees 3,621 records;
7. confirm power present count = 3,621;
8. confirm HR present count = 3,621;
9. independently verify there are 3,620 deltas and every delta is exactly one second;
10. confirm there are no missing/duplicate/backward timestamps in this representative extraction;
11. confirm an eligible best-20-minute result exists;
12. independently verify that result within the tolerance above;
13. confirm the result reports Source ID, extraction ID, method/version, 1,200 samples, start/end context, raw average, and rounded watts;
14. confirm the source session average-power value remains distinct from the best-20-minute application derivation;
15. confirm compact verification output contains no coordinates or full raw stream dump.

Do not hard-code a best-20-minute watt target from Strava or prior research. Derive and independently verify the value from the accepted RideWorks extraction.

If the representative data no longer matches P1-01's accepted 3,621-record complete one-second evidence, stop and report rather than weakening the calculation rules.

## 11. Acceptance criteria

P1-02 is ready for Analyst acceptance only when all of the following are true.

1. Analysis consumes P1-01's application read boundary rather than reparsing external input or using retired application data paths.
2. The Phase 1 FIT source summary remains source-attributed and semantically unchanged.
3. Native ordered timestamp/power/HR evidence is exposed without resampling, smoothing, interpolation, deduplication, or manufactured samples.
4. Zero and missing values remain distinct.
5. Best 20-minute power uses exactly the 1,200-sample half-open-window semantics defined in this JIT.
6. Only exact one-second, complete-power candidate windows are eligible.
7. Missing power is never silently converted to zero.
8. The production result uses native source record power, not FIT/Strava/vendor summary values.
9. Ties select the earliest source-record window.
10. The result retains unrounded watts plus the specified whole-watt presentation value.
11. The result includes Activity, Source, current extraction, and method/version context.
12. No eligible window produces an explicit unavailable result rather than a fabricated value.
13. Re-extraction causes subsequent analysis to use/report the new current extraction.
14. An independently expressed calculation reproduces the representative best-20 result within 0.01 W and exactly matches the selected start index and rounded watts.
15. Representative acceptance re-confirms the accepted 3,621-record complete one-second evidence.
16. Source session average power remains distinct from application-derived best-20-minute power.
17. No generalized derivation persistence framework, source-ranking system, or later-phase analytical feature was introduced.
18. Required verification evidence is committed without personal raw streams or source files.
19. P1-01 tests/regressions remain passing.
20. P1-03 has not begun.

## 12. Stop-and-report conditions

Stop and report rather than broadening the task if:

1. the P1-01 read boundary is materially insufficient and fixing it would change accepted evidence semantics;
2. the representative ride is not the accepted complete one-second/power-complete extraction;
3. selecting a Source requires a new source-ranking/evidence-selection policy;
4. correct best-20 calculation appears to require interpolation/resampling or a general irregular-sampling policy;
5. a new durable analytical schema/framework appears necessary rather than merely convenient;
6. independent verification disagrees with production beyond the declared tolerance;
7. source data exposes a materially unexpected condition that invalidates the defined calculation semantics;
8. implementation would require a product/training-analysis decision not already settled;
9. the final HARD — Analyst gate is reached.

Straightforward implementation defects may be fixed and re-verified within the task.
