# P2-02 — Scalable Activities Browser

**Status:** Analyst-authored JIT; implementation not started  
**Phase:** Phase 2 — Historical context and performance history  
**Task:** P2-02  
**Controlling product:** RideWorks

## 1. Purpose

Replace the Phase 1 one/few-ride Activities list with a practical browser for the full imported RideWorks history.

The rider has **1,434** known historical Activities. P2-02 must make that history easy to scan, search, filter, sort and open without rendering one unbounded page or recreating Strava's full activity-management product.

The interaction direction is intentionally similar to the useful parts of Strava's activity-history browser: a compact filterable/paginated history. Strava is a reference for the general browsing interaction, not a specification of RideWorks columns, controls or visual design.

P2-02 also closes the visible title/enrichment loop from P2-01: when actual Strava-export activity-name evidence exists, RideWorks should present that source title rather than the Phase 1 derived fallback, while keeping title provenance and activity type/subtype distinct.

## 4. Product decisions already settled

P2-02 must implement these settled decisions:

1. All 1,434 imported Activities remain part of RideWorks history.
2. The normal Activities experience is cycling-focused but must allow the rider to include non-cycling history.
3. The list must use bounded pagination rather than an unbounded 1,400-row page.
4. Search by actual activity title/name is required.
5. Activity type/subtype filtering is required.
6. Practical date filtering is required.
7. Useful sorting is required.
8. Actual source title is preferred when available; type/subtype remain separate.
9. Missing evidence remains visibly unavailable rather than fabricated.
10. The whole row/card should open the Activity's stable RideWorks route.
11. Do not add Strava-specific private/deleted/social/tag-management controls unless RideWorks has a real use for them.
12. Manual ride-to-ride comparison is not part of P2-02.

Exact columns, page size, control layout and responsive breakpoints remain implementation discretion.

## 5. Activities route and URL state

Keep the existing Activities destination at:

```
/
```

Filtering/sorting/pagination state should be represented in ordinary GET query parameters so reload/back/forward navigation remains understandable.

The exact parameter names are implementation discretion, but the URL must be able to represent:

- page;
- title search;
- cycling/all or activity-type selection;
- date filter/range;
- sort selection.

Do not add client-side routing or a frontend framework.

Invalid/out-of-range query values must fall back safely or show a compact validation state; they must not cause a 500, leak SQL, or interpolate raw values into SQL.

## 6. Default browsing behavior

Default Activities view:

- newest first;
- cycling-focused;
- first bounded page;
- no title/date search restriction.

"cycling-focused" means the default may show the cycling cohorts represented by the imported source evidence (for example Ride and Virtual Ride) while providing a clear **All activities** option that includes Run/Walk/Rowing history.

Do not delete or hide non-cycling Activities from the data model.

A fixed page size in the approximate **25–50 row** range is appropriate. The exact choice is implementation discretion. User-configurable page-size settings are not required.

The page should show:

- enough result/count context to make the active filter obvious;
- current page and practical previous/next navigation;
- no need to expose hundreds of individual page-number links.

## 7. Narrow presentation policy for browser metadata

P2-02 needs a deterministic display policy; this is a presentation choice, not canonicalization of source evidence.

### 7.1 Title

For the known P2 history:

1. prefer a non-empty Strava-export activity title/name source observation;
2. if multiple Strava-export title observations exist, prefer the most recently imported one for display only;
3. if no source title is available, use the existing explicit derived type/date fallback and label it as derived.

The underlying source observations remain intact and inspectable.

Do not overwrite the Activity with a canonical title field merely to render the list.

### 7.2 Type/subtype

Use imported source activity-type/sport-type evidence where available.

Do not infer "outdoor" or "measured" from Ride/Virtual Ride labels.

Keep title and type/subtype visually distinct.

### 7.3 Date/time

Use the best directly supported activity-start/date evidence available for display/order without assigning a timezone that the source does not establish.

Where an absolute source timestamp exists, display it in the browser's local timezone and treat the **same displayed local calendar date** as the user's date-filter date. A rider should not see an activity as September 29 and have to search September 30 merely because the underlying instant crosses a UTC day boundary.

Where the source date/time has no established timezone/offset, preserve its supplied source calendar date and do not shift it into an invented timezone.

The date-filter semantics must therefore match what the Activities browser presents to the rider: browser-local day for known absolute instants; preserved source day for timezone-unknown evidence.

### 7.4 Summary fields

The browser may show a compact subset such as duration and distance when supported.

Do not create a universal canonical summary layer for the list.

A simple narrow browser presentation policy may select an attributable source value for a row, but missing values remain unavailable and the policy should be obvious in code/tests.

Do not add power-ranking or trusted-performance semantics in P2-02; that belongs to P2-03.

## 8. Search

Title search must:

- operate on actual source activity-title/name evidence;
- be case-insensitive;
- support useful partial matching;
- safely handle punctuation and HTML-sensitive text;
- preserve all other active filters/sort when submitted or paginated.

Search does not need fuzzy matching, stemming, tags or full-text infrastructure.

If a derived fallback is displayed because no source title exists, searching that fallback text is optional; actual source-title search is the requirement.

## 9. Activity-type filter

Provide a practical type filter based on imported source evidence.

Minimum useful choices for the known history:

- Cycling / default;
- All activities;
- individual source activity types when useful, including at least Ride and Virtual Ride.

Run/Walk/Rowing may be individual options or reachable through All; exact control shape is UI discretion.

Do not treat source labels as proof of physical riding conditions.

## 10. Date filter

Provide a practical date filter.

A From/To date range is preferred because it directly covers years and arbitrary periods without a large year-specific UI.

A year shortcut/dropdown may be added if it improves usability, but is not required.

Requirements:

- one-sided ranges are allowed;
- invalid ranges are handled safely;
- filtering is based on source-supported activity date/start evidence;
- for known absolute instants, the filter uses the same browser-local calendar day shown to the rider;
- for timezone-unknown/date-only source evidence, preserve the supplied source calendar day rather than guessing a timezone;
- the UI must not describe a UTC-day filtering rule when the displayed date is local.

## 11. Sorting

Default sort is newest first.

Also provide at least one genuinely useful alternate sort based on evidence already imported, such as:

- oldest first;
- duration;
- distance.

Exact alternate sorts are implementation discretion.

Rules:

- sorting must be deterministic;
- missing values must not be converted to zero;
- ties require a stable secondary key, such as Activity ID;
- sorting must not require loading native streams.

No sort by best-20/power history in P2-02.

## 12. Activity-row/card content

Each result should be compact and information-dense, consistent with the approved RideWorks visual character.

At minimum show:

- preferred/display title in its own Title column/region;
- **Date in its own dedicated column/region**, not as a second line beneath the activity title;
- source activity type/subtype in its own column/region;
- selected compact summary context when available;
- clear affordance that the row opens the Activity.

For known absolute timestamps, the Date column must render the activity in the browser's local timezone. The displayed local date/time and From/To filter semantics must agree.

If the source evidence has no established timezone/offset, do not falsely label it local time. Show the supplied source date/time with an explicit timezone-unknown indication until stronger evidence exists.

Do not turn the page into a generic database/admin table.

Do not add fake Dashboard/Performance/Plan/AI destinations merely to fill the shell.

The current RideWorks persistent shell/brand remains.

## 13. Stable Activity Review routes

Every listed Activity must open its stable route:

```
/activities/<RideWorks Activity ID>
```

P2-02 must stop using the Phase 1 FIT-only list as the authorization check for whether a stable Activity route exists.

### 13.1 Activities with the accepted rich FIT review

For an Activity that still satisfies the accepted Phase 1 rich-review analysis boundary:

- retain the existing chart, summary, best-20 and provenance behavior;
- use the actual source title when available;
- show title provenance accurately;
- keep type/subtype separate;
- do not change best-20 semantics.

### 13.2 Other imported Activities

GPX, TCX and CSV-only Activities must not produce a dead-end 404 merely because the rich FIT analysis is unavailable.

Render a thinner evidence-appropriate Activity Review that contains at least:

- preferred/derived title;
- source-supported date/type context;
- available summary evidence where appropriate;
- associated source/evidence availability/provenance;
- a clear statement that detailed RideWorks review is unavailable where the necessary supported detailed analysis is not yet implemented.

Do **not** invent power/HR charts, best-20, or source substitutions to make these pages resemble FIT review.

If a source has native streams that RideWorks does not yet analyze in the rich review, preserve that distinction: "available source evidence, detailed review not yet supported" is preferable to pretending it is absent.

This thin-review behavior is required so browsing the complete durable history remains useful.

## 14. Source-title enrichment in existing rich Activity Review

The Phase 1 representative is now enriched with Strava-export title evidence.

P2-02 must visibly prove that enrichment:

- Activity list uses the actual source title;
- opening that Activity uses the same actual source title in the review header;
- provenance/details identify the title as source-supplied Strava-export evidence;
- FIT summary/native/chart/best-20 evidence remains attributable to FIT;
- the old derived title fallback is not presented as though it were the source title.

No manual rename system is required.

## 15. Data-access expectations

The browser must not load native record streams for list rendering.

It may:

- extend P2-01's `activity_history()` boundary;
- add a bounded/query-oriented Store helper;
- filter/sort the ~1,434 metadata rows in process if that remains simple and responsive;
- use SQL for filtering/pagination if clearer.

Do not introduce search services, caches, ORM, pagination frameworks or generalized repository layers merely for scale.

The implementation must remain reasonable for this single-rider history.

## 16. Visual direction

The Activities page should feel like the same product as the accepted Phase 1 Activity Review:

- compact persistent shell;
- restrained navy/blue/green RideWorks palette already established;
- clear hierarchy;
- dense but readable table-like rows;
- Date visually separated from Title rather than nested under the title;
- modest borders/surfaces;
- usable filter controls;
- no oversized admin/debug chrome.

The user's Strava screenshots are a **general interaction reference** for history browsing: filter controls above a bounded list with pagination. Do not copy Strava branding, exact columns or exact layout.

P2-02 requires Owner visual/usability review because the browser will become the normal entry point to a 1,400+ activity history.

## 24. Stop-and-report conditions

Stop and report if:

- the P2-01 history read boundary cannot support practical browsing without a materially broader data redesign;
- a deterministic source-title/date/type presentation policy cannot be implemented without silently canonicalizing conflicting evidence;
- full-history list rendering requires native stream loading or is materially unusable without a new infrastructure layer;
- GPX/TCX/CSV-only stable routes require inventing analysis/source-selection policy beyond this JIT;
- existing rich FIT Activity Review or best-20 semantics would need to change materially;
- privacy-safe Owner/browser verification cannot be performed;
- implementation starts expanding into P2-03 performance history, API sync or Phase 3.

Ordinary UI details, bounded query helpers, CSS refinement and safe query parsing are implementation discretion.
