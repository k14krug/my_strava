## 1. Purpose

Determine what RideWorks should mean by training load and current training state
**before** implementing a production Fitness/Fatigue/Form model.

The task should answer:

> Which transparent load/state model best fits this rider, given the evidence
> RideWorks actually has?

This is a research/design task, not production model implementation.

## 4. Start with evidence inventory

Before calculating any longitudinal load model, inventory the accepted RideWorks
store and retained source evidence.

Quantify, by year and Ride/Virtual Ride where useful:

- Activities with eligible detailed power under current evidence policy;
- Activities with power streams that are preserved but intentionally not trusted
  for current Performance/load use;
- Activities with heart-rate streams or reliable HR summaries;
- Activities with duration;
- Activities with known work/kJ;
- overlap between power / HR / duration / work evidence;
- current gaps caused by outdoor-power exclusion;
- any existing athlete-state values embedded in FIT/TCX/GPX/API/export evidence.

Do not perform a historical Strava API crawl for missing training-state inputs.

## 5. Historical athlete-state inventory

Search retained evidence and current application state for date-effective:

- FTP;
- body weight;
- HR max;
- resting HR;
- threshold HR / zones;
- power zones;
- relevant bike/equipment state only where a candidate model truly needs it.

Classify each candidate value as known/supplied/measured/calculated/estimated/
inferred/missing and preserve dates/provenance.

**Hard rule:** today's FTP or weight must not be silently applied backward.

If complete historical FTP is not present, quantify the gap and compare minimal
ways to provide it. A simple dated manual FTP history is a candidate, not yet a
schema decision.

Do **not** infer historical FTP from 20-minute Performance unless the Owner later
approves an explicit inference policy.

## 6. Candidate calculations

Implement exploratory/research calculations outside the production product path.

### A. Classic industry baseline

Evaluate a power-based TSS/CTL/ATL/TSB-style baseline using the documented
formula/decay semantics only where the required historical FTP and eligible
power evidence are available.

Record:

- load input;
- FTP used and its effective date/provenance;
- daily stress;
- short/long load values;
- “form”/balance value;
- missing days due to unavailable evidence.

Do not present CTL as literal physiological fitness or ATL as literal fatigue in
the recommendation without qualification.

### B. Simpler transparent workload baseline

Using the same eligible daily load input where possible, compare a simpler model
such as:

- recent 7-day workload;
- longer 42-day workload;
- EWMA or rolling totals/averages;
- recovery spacing / hard-session count as separate facts.

The purpose is to determine whether RideWorks gets most of the useful signal
without importing stronger fitness-fatigue claims.

### C. HR-derived candidate

If the necessary historical HR reference values exist, evaluate a transparent
HR-based internal-load candidate (e.g. a TRIMP family method).

Keep HR-derived load a separate evidence/method class. Do not numerically merge
it with power-derived load merely to create a complete chart.

If reference HR state is unavailable, record that limitation rather than
manufacturing it.

### D. External/context signals

Inventory and, where useful, plot context such as duration, known work/kJ,
hard-session spacing, races/demanding sessions and Performance-v2 changes.

Do not turn unlike quantities into one arbitrary point scale without an explicit
model and justification.

## 7. Current evidence policy

For P4-01:

- Virtual Ride file/API detailed power accepted under current Performance-v2
  evidence rules may be evaluated for power-based load;
- file and API provenance remain distinguishable;
- outdoor Ride power remains **excluded** from the power-load baseline;
- Strava summary average watts are not a substitute for a detailed eligible
  power stream;
- estimated outdoor power is not introduced;
- no GPX-coordinate-derived power/load.

Quantify rather than hide the resulting coverage gap.

## 8. Model comparison

Compare candidates on:

- historical coverage;
- dependence on missing historical athlete state;
- transparency;
- reproducibility;
- sensitivity to hard/easy/rest periods;
- stability/noise;
- response around known demanding sessions;
- relationship with Performance-v2 trend and notable best-20 periods;
- behavior during missing-data periods;
- usefulness for a single rider reviewing current state.

Do not fit free parameters aggressively to best-20 history. Performance outcomes
are sparse and should be used for sanity checking, not as a target that the model
must be trained to reproduce.

## 9. Research requirements

Verify current authoritative/primary sources.

At minimum cover:

- current TrainingPeaks documentation for TSS and CTL/ATL/TSB as an industry
  reference;
- Banister impulse-response basis and published limitations;
- recent peer-reviewed work on power-based training-load / fitness-fatigue
  modeling;
- HR-derived load limitations if recommending HR fallback.

Identify which conclusions come from:

- established practice;
- current research/documentation;
- RideWorks historical evidence;
- inference/design recommendation.

Sauce may be consulted as a reference implementation if relevant, but it is not
an authority.
