# P2-05 — Incremental Strava synchronization

**Status:** Analyst-authored JIT; implementation not started  
**Phase:** Phase 2 — Historical context and performance history  
**Task:** P2-05  
**Controlling product:** RideWorks  
**Authoritative API review date:** 2026-10-05

## 1. Purpose

Finish Phase 2 with a normal forward-looking Strava synchronization path.

RideWorks already owns the historical baseline imported from the user's Strava bulk export. P2-05 is **not** a second historical-ingest system. It should let the rider connect RideWorks to Strava, then explicitly ask RideWorks to fetch recent/new activity metadata so that post-export activities can enter or enrich the durable RideWorks history.

The first implementation is intentionally private, single-rider and user-invoked. No background cloud service, polling daemon, multi-user account system or historical API crawler is needed.

## 4. Current authoritative Strava behavior verified for this JIT

The following was re-verified from current Strava documentation on 2026-10-05.

### 4.1 OAuth / token behavior

Official source: <https://developers.strava.com/docs/authentication/>

- Strava API v3 uses OAuth2.
- Applications exchange an authorization code for a short-lived access token plus refresh token.
- Access tokens expire after roughly six hours.
- Refresh responses may rotate the refresh token; RideWorks must atomically retain the **latest returned refresh token** and must not keep using an older one after rotation.
- Applications must inspect the scopes actually granted.
- Requested scopes should be limited to what the application needs.

For P2-05, request **`activity:read_all`** so the rider's own Only You activities are not silently omitted. Do not request write/profile scopes.

### 4.2 Activity listing

Official source: <https://developers.strava.com/docs/reference/>

`GET /athlete/activities` supports:

- `after` epoch timestamp;
- `before` epoch timestamp;
- page number;
- `per_page` (default 30);

and returns `SummaryActivity` objects.

P2-05 should use this list endpoint as the normal sync source. Do not fetch per-activity streams, laps, zones, segments, comments, kudos or photos in this task.

A per-activity detail request is allowed only if implementation discovers a specific required field that is unavailable from the summary object and the extra request is justified in the verification report. Do not add detailed requests reflexively.

### 4.3 Rate limits

Official source: <https://developers.strava.com/docs/rate-limits/>

Current default application limits are documented as:

- overall: 200 requests / 15 minutes and 2,000 / day;
- non-upload/read-oriented: 100 requests / 15 minutes and 1,000 / day.

Every response exposes rate-limit headers including:

- `X-RateLimit-Limit`
- `X-RateLimit-Usage`
- `X-ReadRateLimit-Limit`
- `X-ReadRateLimit-Usage`

A 429 is a normal explicit rate-limit failure, not a reason to retry aggressively.

RideWorks must:

- record/report compact rate-limit state from responses;
- stop cleanly before or on an exhausted limit;
- never busy-retry a 429;
- never build concurrency merely to increase throughput.

For this single-rider user-invoked workflow, expected request volume should be tiny.

### 4.4 Single-player capacity

The current rate-limit documentation states newly created apps start with athlete capacity 1 ("Single Player Mode"). That fits RideWorks' private single-rider use case. No multi-athlete access request is part of P2-05.

### 4.5 Webhooks

Official sources:

- <https://developers.strava.com/docs/webhooks/>
- <https://developers.strava.com/docs/getting-started/>

Strava currently documents webhooks for activity create/update/delete events and athlete deauthorization, and specifically points developers to webhooks rather than activity polling. A webhook subscription requires an externally reachable callback URL; each application may have one subscription.

**P2-05 does not introduce public hosting solely to receive webhooks.** The accepted Phase 2 product contract explicitly permits a user-invoked first sync and does not require background cloud infrastructure.

Therefore the Phase 2 mode is deliberately:

- manual/user-invoked;
- no polling loop;
- no claim of real-time synchronization;
- explicit handling of token revocation/401 when a manual sync occurs;
- explicit local Disconnect capability.

Before RideWorks gains unattended/background synchronization or is deployed as a public/always-connected integration, webhook support must be revisited and treated as a prerequisite.

Do not fake a webhook subscription or build an evasion mechanism.

### 4.6 Current API policy / retention tension

Official sources:

- <https://www.strava.com/legal/api>
- <https://www.strava.com/legal/api_policy>

The current policy effective 2026-06-01 states, among other things, a seven-day cache limit and deletion obligations on user revocation/termination.

This conflicts with RideWorks' previously settled Owner decision to retain useful API-derived evidence as part of the rider's durable personal training history. The Owner has explicitly accepted the practical policy risk of retaining useful API information.

P2-05 must therefore:

- document the current policy accurately;
- retain API provenance visibly;
- avoid concealing API use;
- avoid bulk historical API harvesting;
- avoid collecting unnecessary API fields;
- keep all data single-rider/local;
- **not** redesign RideWorks around pretending API-derived evidence can never persist.

This is a known project-policy risk, not an implementation bug and not permission to evade Strava controls.

## 5. User workflow

The **normal rider workflow must be available inside the running RideWorks web application**. The CLI commands remain supported as a secondary maintenance/recovery/test path, but the Owner must not need a second terminal or server restart merely to connect or synchronize Strava.

Add one small **Settings** destination to the existing RideWorks shell/navigation. Do not build a generalized admin/configuration framework.

The Settings page must contain a compact **Strava** section showing:

- connection status: Connected / Not connected / Authorization needs attention;
- whether Strava client credentials are configured, without displaying either credential;
- **Connect Strava** when disconnected;
- **Sync now** when connected;
- last successful sync time when available;
- compact last-sync outcome when available (for example new / enriched / unchanged counts);
- **Disconnect** when connected;
- a short note that synchronization is manual in Phase 2 and does not run continuously.

The existing commands remain valid:

```bash
.venv/bin/python -m rideworks --data-dir <data-dir> strava-connect
.venv/bin/python -m rideworks --data-dir <data-dir> sync-strava
.venv/bin/python -m rideworks --data-dir <data-dir> strava-disconnect
```

The web and CLI paths must call the same underlying Strava/token/sync logic rather than implementing two separate synchronization systems.

### 5.1 Connect

The normal web **Connect Strava** action should:

1. require locally configured Strava client ID/secret;
2. generate a cryptographically random OAuth `state`;
3. redirect the browser to Strava authorization;
4. request only `activity:read_all`;
5. receive the OAuth callback in the already-running RideWorks server;
6. exchange the authorization code;
7. verify granted scope and authenticated athlete identity;
8. store the current access/refresh token state locally and privately;
9. return the browser to Settings with a clear Connected or actionable failure state;
10. never expose secrets/tokens in HTML, URLs after callback processing, logs or error text.

The CLI `strava-connect` may retain its temporary loopback callback for maintenance/testing, but normal in-app Connect must not require starting a second callback server or restarting RideWorks.

The underlying connect logic should:

1. require locally configured Strava client ID/secret;
2. create a cryptographically random OAuth `state`;
3. start a temporary loopback callback or otherwise provide a simple browser authorization flow;
4. request only `activity:read_all`;
5. exchange the authorization code;
6. verify the granted scope and authenticated athlete identity;
7. store the current access/refresh token state locally and privately;
8. never print secrets/tokens.

The running RideWorks server callback must remain loopback-only for this private local application. If the configured Strava application cannot authorize the required loopback callback, show a clear setup error. Do not silently add a public service/tunnel.

### 5.2 Sync

The normal web **Sync now** action should invoke the same sync operation as `sync-strava` and:

- require an established local connection;
- refresh an expired/near-expiry access token using the latest refresh token;
- fetch only the forward/recent activity window;
- upsert Strava API source evidence idempotently;
- create or conservatively enrich RideWorks Activities;
- persist a successful-sync checkpoint only after the sync transaction completes successfully;
- return the Settings page with a compact human-readable result such as new / enriched / unchanged counts and last successful sync time;
- retain the CLI command's aggregate JSON report for maintenance/verification.

The web request may execute synchronously for the expected small single-rider sync. Do not add a background job queue merely to make the button asynchronous. The UI must prevent or clearly reject a second concurrent Strava operation while one is running.

### 5.3 Disconnect

The normal web **Disconnect** action and the CLI `strava-disconnect` should use the same underlying disconnect behavior and:

- use Strava's currently recommended `POST /oauth/revoke` endpoint when practical;
- remove local access/refresh token state even if remote revocation has already occurred;
- leave a clear disconnected status.

Do not silently delete durable RideWorks activity history as part of ordinary disconnect. The current Strava-policy deletion tension is already explicitly documented in §4.6 and remains an Owner policy decision.

### 5.4 Web action safety

Connect, Sync now and Disconnect change local/external state and therefore must be explicit **POST-style actions**, not state-changing GET links.

For the local single-user server:

- keep the existing loopback-only bind;
- require a per-session/request CSRF-style nonce or equivalent same-origin action token for state-changing Settings actions;
- never put client secret, access token or refresh token into page markup, query strings or browser storage;
- after OAuth callback processing, redirect to a clean Settings URL so the one-use authorization code is not left in browser history as the active page;
- render compact actionable errors without secret-bearing exception text;
- do not introduce accounts/login/session infrastructure merely for this local workflow.

## 6. Local credential/token storage

Extend configuration narrowly.

Safe config names may include:

- `STRAVA_CLIENT_ID`
- `STRAVA_CLIENT_SECRET`
- optional callback port/URI only if needed

Client credentials remain in exported environment or the ignored repository `.env`; do not store them in SQLite or commit them.

The repository's safe `.env.example` **must include commented/example entries for**:

```
STRAVA_CLIENT_ID=
STRAVA_CLIENT_SECRET=
```

so the Owner has an obvious configuration path. The P2-05 README/setup instructions must explicitly tell the Owner to copy `.env.example` to the ignored `.env`, enter the Strava application credentials there, and then run `strava-connect`. Do not require the Owner to infer variable names from source code or reconstruct an older configuration file.

The setup documentation should also state the callback RideWorks will use (default `http://127.0.0.1:8772/strava/callback`) and what matching Strava application callback/authorization-domain setting is required. If current Strava application configuration uses a domain rather than a full callback URI, describe exactly what the Owner should enter.

For the in-app flow, document the callback route on the running RideWorks server as well. The Settings page may report only **Configured / Missing** for client credentials; it must never echo their values.

OAuth access/refresh tokens belong under the private RideWorks data directory, not the repository. Use a small explicit token/state file or similarly narrow local representation with restrictive permissions.

Requirements:

- atomic replacement when refresh token rotates;
- token file never appears in inspect/report/browser output;
- no token/client secret in exceptions, URLs, logs, test fixtures or screenshots;
- tests use fake credentials/tokens only.

Do not introduce a secrets framework/keychain abstraction merely because a commercial app might need one.

## 7. Forward-only sync window

Do not use the API to crawl the historical archive already owned by RideWorks.

### 7.1 Initial sync

Establish the initial API window from the latest known Strava-export baseline, with a **small conservative overlap** around that boundary so the last exported activities can prove enrichment/idempotence and timezone boundaries cannot create a gap.

Preferred rule:

- determine the latest calendar day represented by imported Strava-export source evidence;
- begin the initial API request no more than a few days before that boundary;
- document the exact overlap chosen.

Do not issue page-by-page requests back through years of history.

If the latest export boundary cannot be determined safely from stored evidence, stop and report rather than falling back to "fetch everything."

### 7.2 Later syncs

Persist a last-successful-sync wall-clock checkpoint.

Subsequent manual syncs may use a small fixed overlap before that checkpoint to tolerate API processing delay and recent title/type edits. The overlap should remain measured in days, not months/years.

Every response is idempotently reconciled by Strava activity ID, so overlap must not create duplicate evidence/Activities.

This first manual path does **not** promise detection of arbitrarily old back-dated uploads or edits made far outside the overlap. That requires webhook/event support or a different explicit refresh workflow and is not Phase 2 scope.

## 8. API evidence to retain

Keep the initial allowlist narrow and useful.

At minimum retain, with retrieval timestamp and mapping/version context where practical:

- Strava activity ID;
- activity name/title;
- type;
- sport_type;
- start_date;
- start_date_local if supplied;
- timezone / UTC offset if supplied;
- elapsed_time;
- moving_time;
- distance;
- total_elevation_gain;
- trainer;
- commute;
- manual;
- workout_type when supplied;
- external_id when supplied;
- upload_id when supplied;
- gear_id when supplied;
- device_watts when supplied;
- useful source summary power/HR/cadence values when supplied, **as Strava source evidence only**;
- visibility/private status if supplied and useful to explain access behavior.

Do **not** retain in P2-05 merely because they are present:

- map polylines;
- start/end coordinates;
- privacy-zone geometry;
- comments/kudos/social counts;
- photos;
- segments/efforts;
- leaderboards;
- arbitrary athlete profile fields.

Description/private notes are not required by P2-05. Do not normalize them unless the Owner separately decides they are useful.

The retained API observation should be source-attributable and reproducible enough to explain what RideWorks received without pretending it is an immutable original artifact.

## 9. Source/storage representation

Use the accepted source-centered model.

A Strava API observation is a **Source observation**, not an Activity identity and not a replacement for the Strava-export row/FIT/TCX/GPX source.

Prefer a small specific schema extension rather than generalized EAV.

Implementation may use, for example:

- one API-source table keyed by Strava activity ID + observation/version identity; or
- a narrow API observation table associated with Activity.

Required behavior matters more than the exact table shape:

- latest useful API observation is queryable;
- older differing API observations may be retained if doing so stays simple and helps provenance;
- an identical re-fetch is idempotent;
- external Strava ID is indexed/unique for current association purposes;
- source title/type values remain separately attributable;
- API evidence never overwrites FIT/source summaries.

Do not store OAuth tokens in this schema.

## 10. Activity association

Association must remain conservative.

Use this order:

1. **Established Strava identity:** if this Strava activity ID is already present in Strava-export/API evidence, enrich that same RideWorks Activity.
2. **Strong local-source match:** if no Strava identity is established, allow association to exactly one existing Activity only when multiple independent facts strongly agree, such as:
   - compatible absolute start instant;
   - compatible activity/sport classification;
   - elapsed/moving duration agreement;
   - distance agreement when both sides provide it;
   - exact external/source filename identity if available.
3. If the evidence is ambiguous or conflicting, create a new API-backed Activity rather than forcing a merge, and report that association as unresolved/new.

Do not merge on title alone.

Do not use broad fuzzy matching.

Do not move Sources between two already-established Activities automatically if doing so would require a new reconciliation/merge policy. Stop and report that case.

## 11. Display/title behavior

The Activities browser and Activity Review should understand Strava API evidence.

For the same Strava activity ID, a newer non-empty API title may be preferred over the older Strava-export title because it is later evidence from the same upstream activity. Preserve both source observations.

Type/sport type remain separate from title.

An API-only Activity gets an evidence-appropriate thin Activity Review. Do not fabricate native streams or trusted best-20 analysis.

If an API observation enriches a supported existing FIT Activity, the accepted rich Activity Review remains rich; source title/provenance may update without altering FIT summaries/native records.

## 12. Performance-history boundary

P2-05 does not change P2-03 trusted power eligibility.

Strava API summary watts and any other API summary values:

- remain Strava source evidence;
- do not become native power;
- do not enter `best-average-power-v1`;
- do not make an API-only activity eligible for trusted Performance history.

If synchronization changes classification/source context such that an existing persisted Performance result becomes stale under the accepted input-signature rules, it may become unavailable until the user explicitly rebuilds Performance.

`sync-strava` / **Sync now** must **not** automatically scan historical native streams or rebuild Performance as a hidden side effect. It should report that a rebuild is needed.

### 12.1 Explicit in-app Performance rebuild

When current Performance history has one or more pending/stale Activities, RideWorks must expose an explicit **Rebuild Performance** action inside the running application.

Requirements:

- normal rider use must not require the CLI `rebuild-performance` command;
- the web action must call the same accepted `rebuild_performance(store)` logic used by the CLI, not a second algorithm;
- the action must be POST-style and use the same local action-nonce/same-origin protection as other Settings mutations;
- the rebuild remains all-or-nothing under the accepted Performance transaction semantics;
- no rebuild runs automatically as part of Strava sync;
- after success, the UI must show a compact result and the stale/pending warning must disappear when no stale/pending results remain;
- after failure, the warning remains and the UI reports an actionable failure without exposing private paths/SQL/source data;
- the CLI `rebuild-performance` remains a secondary maintenance/recovery path.

The explicit action may run synchronously for the current ~1,400-Activity private store. Do not introduce a background job queue unless real measured runtime makes synchronous use impractical.

## 13. Updates and deletions

Within the manual overlap window, a changed Strava title/type/metadata should create/update source evidence idempotently and become visible through the accepted display rules.

Do not infer that an activity was deleted merely because it is absent from one paginated/list response.

Because P2-05 does not provide a continuously reachable webhook service, complete real-time detection of arbitrary older deletes/privacy changes is outside this local manual-sync slice.

A 401/invalid refresh token during manual sync must:

- stop clearly;
- mark the local connection unusable/disconnected as appropriate;
- never retry with stale credentials indefinitely.

Do not delete unrelated durable source history on an authentication error.

## 14. HTTP/API client behavior

Use the Python standard library unless a small existing dependency already in RideWorks clearly simplifies OAuth/HTTP behavior.

Required client behavior:

- HTTPS only;
- finite connect/read timeout;
- explicit User-Agent identifying RideWorks;
- Bearer access token only in Authorization header;
- JSON size/shape validation;
- clear handling of 200/4xx/5xx;
- no secret-bearing exception text;
- deterministic pagination until a short/empty page;
- stop/report 429 rather than aggressive retry;
- inspect rate-limit headers on every response;
- no parallel request fan-out.

Do not create a generic HTTP framework.

## 15. Sync transaction / failure semantics

One sync may make multiple API requests, but durable changes should be committed coherently.

Preferred behavior:

- fetch/validate one page;
- accumulate compact validated observations;
- apply them in one Store write transaction at successful end;
- update sync checkpoint in that same successful transaction.

If a later page fails:

- do not advance the successful checkpoint;
- either leave no new durable observations from that run, or retain already-applied pages only if the implementation has explicit resumable semantics and proves idempotence;
- do not leave silent half-sync state.

For the small expected single-rider volume, all-or-nothing application is preferred.

## 19. Web/browser Owner experience

P2-05 now requires a small in-app Settings experience because the Owner should not need terminal commands for normal Strava operation.

Add a **Settings** navigation item/destination consistent with the accepted RideWorks shell. The Settings page should remain deliberately sparse and polished, with one Strava connection card/section.

### Required states

#### Credentials missing

Show:

- Strava: Not configured;
- client credentials: Missing;
- concise instruction to populate the ignored `.env`;
- no Connect button that can only fail mysteriously.

Do not show secret values.

#### Credentials configured, not connected

Show:

- Strava: Not connected;
- client credentials: Configured;
- **Connect Strava**.

#### Connected

Show:

- Strava: Connected;
- **Sync now**;
- last successful sync time if one exists;
- compact last-sync outcome if one exists;
- when Performance is pending/stale, a clear **Rebuild Performance** action with the affected count;
- **Disconnect** as a secondary/destructive action;
- manual-sync explanation.

#### Authorization invalid/revoked

Show an actionable state such as:

- Authorization needs attention;
- **Reconnect Strava**;
- retain durable RideWorks history.

### Persistent Performance-update reminder

If `performance_history(store)` reports any current pending/stale results, RideWorks must keep that condition visible until it is resolved.

Use a compact app-wide alert/banner in the normal RideWorks shell, for example:

> **Performance update needed** — 4 activities changed since the last Performance rebuild. **Rebuild Performance**

Behavior:

- show the alert on Settings, Activities, Performance and Activity Review pages so it is not forgotten merely by navigating away from Settings;
- include the current affected count when available;
- link/action should take the rider directly to the explicit rebuild action or its Settings section;
- do not use alarmist red/error styling for an expected maintenance state; use a noticeable neutral/warning treatment;
- persist naturally across RideWorks restarts because the alert is derived from current stored Performance/input state, not from a transient browser flag;
- disappear automatically once a successful rebuild leaves zero pending/stale results;
- if a rebuild fails, keep the alert visible;
- do not allow the alert to be permanently dismissed while stale/pending results still exist;
- do not invent a separate persisted reminder table solely for this; derive it from the accepted Performance freshness check.

The alert should explain the consequence in plain language: affected Performance/recent-context results are temporarily hidden until rebuilt. It should not imply ride/source data was lost.

### Sync feedback

After **Sync now**, the rider should immediately understand what happened. Show compact counts such as:

- new Activities;
- existing Activities enriched;
- unchanged observations;
- ambiguous/new associations when non-zero;
- whether a Performance rebuild is recommended;
- final success/failure.

Do not display raw Strava activity IDs, tokens, coordinates or developer-only payload details.

The normal workflow should be:

```
Open RideWorks
→ Settings
→ Connect Strava (first time only)
→ authorize at Strava
→ return to Settings
→ Sync now
→ open Activities / refresh history
```

No RideWorks restart and no second terminal should be required for that workflow.

The CLI remains documented as a secondary maintenance/recovery interface and is still used by automated/local verification where convenient.

Owner review should judge whether this feels like a natural RideWorks feature rather than developer plumbing.
