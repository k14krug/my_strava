## 3. Owner-set decisions

These are requirements, not open implementation questions:

- Virtual Ride mileage counts toward the annual cycling mileage goal.
- Outdoor Ride mileage counts.
- File-backed distance takes precedence when available.
- Reuse accepted `history.presentation` distance selection:
  file-backed understood distance → current Strava API distance → unavailable.
- Never infer unspecified CSV distance units.
- Annual mileage is the first narrow goal; do not build a generic goal system.
- Do not implement Fitness Score, Training Load, Next Workout, adaptive plan,
  FTP update suggestions or a full power curve in this task.

## 4. Implementation boundary

Implement the complete `docs/PHASE_3_ACCEPTANCE.md` contract with the smallest

Expected areas include:

- a narrow year-specific annual mileage-goal persistence migration;
- Settings UI/action for the current-year mileage goal;
- a read-only dashboard aggregation module or similarly small boundary;
- Home dashboard at `/`;
- Activities browser moved to `/activities`;

- tests and verification report.

## 5. Data/storage guidance

A simple table such as a year-keyed annual-mileage-goal record is appropriate.

Keep the stored goal as the rider's explicit target. Do not materialize cheap
YTD/weekly aggregates.

If storing the target in miles, retain that semantic explicitly; do not pretend
it is source-measured meters. If converting to meters internally, retain/display
the rider-entered miles without manufacturing extra precision.

Migration must preserve all accepted schema-6 data and originals.

## 6. Dashboard aggregation

Build dashboard aggregates from `store.activity_history()` +
`history.presentation(snapshot)` and current Performance history.

Cycling contribution rules and evidence order are exactly those in the Phase 3
contract.

Do not read raw FIT/Strava stream samples merely to calculate mileage.

Return explicit diagnostic/provenance counts for file/API/missing distance and
missing dates.

## 7. Timezone

Home must know the browser timezone before final server-side period aggregation.

Use a bounded query parameter such as `tz`, validated with `zoneinfo`, and a
small JS redirect/update pattern comparable to the accepted Activities browser.

Do not calculate YTD/weekly calendar membership in server-local time.

## 8. Dashboard first cut

Implement the dashboard subset in the acceptance contract:

- This Week Miles card (actual Monday-through-current-local-date cycling distance);
- Last 7 Days card;
- Current 42-day best card;
- Latest eligible 20-minute ride card;
- recent cycling Activities;
- mileage-progress visualization;
- compact 20-minute Performance visualization/snapshot;
- deterministic useful insight(s) when supported;
- optional last-successful-sync status.

When annual target is absent, show YTD actual + direct Set annual goal path.

The mockup is layout inspiration, not pixel parity.

### 8.1 Owner dashboard correction — 2026-10-07

The first Owner review found the YTD goal duplicated between the top summary
cards and Mileage Progress. Correct the dashboard before Gate 1 approval:

- remove the top **YTD mileage goal** card;
- replace it with **This Week Miles**, showing actual cycling miles from the
  current local Monday through today;
- keep annual-goal actual/target/progress information in **Mileage Progress**
  only;
- under YTD mileage/progress show:
  - miles remaining;
  - **needed average miles per week from now to December 31**.

The needed-weekly value is a goal-progress arithmetic value, not a training
recommendation.

For a current local date `d` after today's already-recorded mileage has been
included:

```
remaining_miles = max(0, annual_target - actual_ytd)
remaining_calendar_days = max(0, Jan 1 next year - (d + 1 day))
needed_miles_per_week =
    0                                  if remaining_miles == 0
    Unavailable                        if remaining_calendar_days == 0 and remaining_miles > 0
    remaining_miles / (remaining_calendar_days / 7) otherwise
```

Display this as **Needed average: N.N mi/week** (or equivalent clear wording).
The independent verifier must reproduce it.

#### Mileage Progress chart correction

The weekly chart becomes a combined actual/required-pace view:

- completed-week bars show **actual cycling miles** for those completed
  Monday–Sunday weeks;
- overlay a line with one point per displayed week showing the **average
  miles/week that were still required after that week's actual mileage was
  complete** to reach the annual target by year end;
- for each completed week ending on Sunday `e`, calculate the point from:
  - cumulative actual YTD miles through `e`;
  - remaining target after `e`;
  - remaining calendar days from `e + 1 day` through December 31;
- the current partial week is different: its bar must show the **current needed
  average miles/week going forward**, not partial week-to-date actual mileage;
- visually distinguish that current needed bar from completed actual bars;
- the current required-line endpoint uses the same current-as-of calculation,
  so it agrees with the needed/week value shown under YTD progress;
- retain actual current-week-to-date mileage in the dashboard payload/details
  and the **This Week Miles** top card even though the chart's current bar is
  the required-going-forward value;
- when the annual goal is already met, required pace is zero;
- when the year has ended with remaining miles, required pace is Unavailable
  rather than infinity or manufactured precision.

Chart legend/caption must make the mixed semantics explicit:
**completed bars = actual; current bar + line = needed average/week**.

#### Mileage chart interaction

Do not rely on native SVG `<title>` hover timing.

Implement an immediate RideWorks tooltip/readout for weekly bars/required points:

- show on pointer enter/move without the browser's delayed native-title wait;
- tooltip content is **only the mileage value and unit**, e.g. `57.3 mi`;
- do not include the date/week label in the tooltip;
- hide immediately on pointer leave;
- keyboard focus must expose the same value without requiring a mouse;
- avoid duplicate delayed browser tooltips.

#### Recent Activities Avg Pwr

Add an **Avg Pwr** column to Recent Activities.

Select average-power evidence narrowly for dashboard presentation:

1. understood file-backed session `avg_power`;
2. if needed for an understood single-lap TCX source, that lap's `avg_power`;
3. otherwise current Strava API summary `average_watts`;
4. otherwise Unavailable.

File-backed average power therefore takes precedence over conflicting API
summary average power, matching the Owner's source-preference direction without
creating a universal canonical power value.

Do not use Strava CSV summary watts, do not calculate the Recent Activities
column from stream samples, and do not change Performance-v2 eligibility or
best-20 semantics.

Add tests and independent verification for all of the above. Re-present
**HARD — Owner** after correction.

## 11. Independent verification

Production aggregation functions must not be their own acceptance oracle.

Create a compact independent verifier that scans durable Activity/source
evidence separately enough to validate:

- YTD miles;
- trailing seven days;
- previous seven days;
- weekly recent buckets;
- file/API distance contribution counts;
- goal percent/remaining/calendar pace;
- current Performance summary references.

Use Decimal or another explicit strategy where useful to avoid presentation
rounding becoming the calculation oracle.
