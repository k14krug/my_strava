# P1-01 — Durable Single-FIT Activity Import

**Status:** Analyst-authored JIT; implementation not started  
**Phase:** Phase 1 — Useful single-ride review  
**Task:** P1-01  
**Controlling product:** RideWorks

## 1. Purpose

Implement the first durable RideWorks application slice: import one FIT activity into application-owned storage as a durable **Activity + Source**, preserve the original artifact unchanged, and persist the minimum typed normalized evidence and native timing needed by later Phase 1 analysis.

This task creates real RideWorks application data. It is not another research experiment.

The user-facing capability enabled by this task is foundational but concrete: the representative ride can enter RideWorks once, survive process restart, retain its original evidence, be reopened programmatically by stable application identity, and be re-extracted without reacquiring the source file.

P1-01 does **not** calculate best 20-minute power and does not build the Activity Review UI. Those belong to P1-02 and P1-03.

## 2. Background / question being answered

Phase 1 asks:

> Import one real representative ride and review it well enough that the rider can understand how the ride went without opening Strava.

P1-01 supplies the durable evidence boundary required for that product outcome.

Prior work established:

- application-owned Activity identity is independent of Strava and source-file identity;
- a Source owns imported evidence;
- original artifacts remain unchanged;
- normalized evidence is typed and rebuildable from the original;
- native timing is preserved rather than silently regularized;
- source summaries and later application derivations remain distinct;
- artifact hashes identify artifacts, not Activities;
- multiple Sources must remain possible later, but Phase 1 does not need to demonstrate real source enrichment;
- historical athlete/equipment state is independent and time-aware;
- the retired Strava application imposes no compatibility or architecture constraints on RideWorks.

Two independent Astra readiness reviews concluded that the project is ready to author this JIT and begin Phase 1. The second review found no new blocker before P1-01.

The implementation question is therefore deliberately narrow:

> What is the simplest durable local RideWorks representation that faithfully imports the representative FIT, can be safely reopened/rebuilt, and gives P1-02 a trustworthy read boundary without turning this task into final application architecture?

### Supported P1-01 input envelope

Packaging and parseable content format are distinct metadata:

- packaging: plain or gzip;
- content format: FIT.

Do not infer validity only from filename suffix. Invalid gzip or invalid FIT content must fail clearly.

### Multiple sessions / unsupported content

P1-01 is a single-activity FIT importer.

If a candidate FIT contains a structure that cannot safely be represented as one Activity under this JIT—for example multiple activity sessions where selecting one would require policy—fail clearly **before creating a completed Activity/Source**.

### Source safety

Never modify the supplied input file in place.

The importer must copy received bytes into RideWorks-managed staging/storage and parse the RideWorks-managed copy, not depend on the external file after a successful import.

`fitdecode==0.11.0` was used successfully in the archive research and was verified as the current PyPI release on 2026-10-02. It includes an updated FIT profile and remains appropriate for this bounded importer.

Create a clean RideWorks dependency/package declaration, preferably `pyproject.toml`, rather than extending the retired application's `requirements.txt` as though that legacy stack were authoritative.

Do not add an ORM, migration framework, web framework, dataframe stack, or general application framework for P1-01 unless a concrete task requirement proves it necessary. If such a need appears, stop for Analyst review.

### 8.3 Application-data location

RideWorks data must live outside the Git repository by default and remain stable across process restart and changes in current working directory.

Use this simple precedence:

1. explicit CLI `--data-dir` when supplied;
2. `RIDEWORKS_DATA_DIR` environment variable when set;
3. default `~/.rideworks`.

The data directory is private runtime data and must not be committed.

Expected logical layout:

```text

    originals/

```

The exact safe filename/path organization under `originals/` may vary, but it must be deterministic, collision-safe, and not depend on the external source path remaining available.

Tests must use temporary data directories rather than the real user directory.

### 8.4 Minimum durable physical representation

Use one SQLite database for the P1-01 durable metadata/normalized evidence.

The exact SQL table/column names are implementation detail, but the persisted semantics must support at least the following.

#### Activity

Persist a deliberately small Activity record containing:

- application-owned Activity ID;
- lifecycle/creation metadata needed for durability.

Use an application-generated ID independent of Strava, filename, or artifact hash. A UUID generated by Python's standard library is appropriate.

Do not create provenance-free canonical distance/power/HR/etc. fields on Activity.

#### Source

Persist a distinct Source associated with the Activity, including:

- application-owned Source ID;
- Activity ID;
- source kind sufficient to identify a file/FIT source;
- association basis: this Activity was created directly from this imported Source;
- original basename for human inspection;
- received byte size;
- SHA-256 of the exact received artifact bytes;
- packaging: plain or gzip;
- parseable content format: FIT;
- application-managed stored-artifact relative path;
- import timestamp.

The artifact hash identifies the exact artifact. It is not the Activity ID.

Do not require or invent a Strava ID.

#### Extraction identity

Each successful current normalized extraction must have an identity/context including:

- extraction ID or equivalent durable revision identity;
- Source ID;
- parser name;
- parser version;
- RideWorks extraction/mapping version;
- extraction timestamp;
- source-artifact hash/input identity.

P1-02 must be able to identify exactly which current extraction its later calculations consume.

A successful re-extraction must change the extraction identity/revision even when it reproduces the same values.

P1-01 does not need to retain every obsolete extraction snapshot. Later derivations will use the extraction identity to recognize that their inputs are stale when the Source's current extraction changes.

#### FIT source/session summary

For the single supported FIT session, inspect and persist typed source evidence for at least:

- start/date-time evidence available from FIT;
- sport;
- sub-sport/activity subtype when present;
- total elapsed duration;
- total timer duration;
- distance;
- total ascent/elevation gain when present;
- average power;
- maximum power;
- average heart rate;
- maximum heart rate;
- average cadence.

Use FIT-decoded source units/semantics, not presentation conversions such as miles merely for storage convenience.

Elapsed and timer duration remain separate. Do not relabel timer time as moving time and do not force the two values to agree.

If a required inspected session field is absent, persist absence/null as source evidence; do not substitute zero or another source.

#### Native record evidence

Persist ordered record evidence sufficient for Phase 1 power/HR analysis:

- extraction identity;
- stable source-record order/index;
- decoded record timestamp when present;
- power when present;
- heart rate when present.

Record order must remain independently available from timestamp. Timestamp must not be used as the sole unique sample key because other FIT files can contain duplicates.

Legitimate zero power remains zero.

Missing power/HR remains missing/null; do not remove the record to make a dense signal and do not substitute zero.

P1-01 does not need to persist every FIT record field. Other fields remain recoverable from the preserved original and may be added by a later extraction version.

#### Signal availability

For at least power and heart rate, retain compact extraction-level evidence sufficient to distinguish:

- signal present;
- signal observed absent in the inspected records;
- present with missing samples.

Retain total record count, present-value count, and missing-value count or equivalent facts.

Do not use one overloaded status to represent both source provenance and availability.

Additional FIT fields not included in the P1-01 extraction are **not extracted**; do not describe them as observed absent merely because they have no database column.

#### Origin/provenance

All imported normalized evidence is attributable to its FIT Source.

Do not label FIT power as `measured` merely because a power field exists.

For P1-01, source attribution and origin classification are separate. Where the artifact does not explicitly establish measured/estimated/calculated origin, use `unknown` or leave origin unasserted rather than inventing certainty.

#### Lap/event timing

Preserve enough typed lap/event timing structure to avoid losing meaningful FIT timing semantics required by DESIGN-002.

At minimum retain, where present:

- source order/index;
- lap start/timestamp boundaries;
- lap elapsed/timer duration;
- event timestamp;
- event name/type;
- timer-related event detail when supplied and understood.

Do not create a complete generic FIT message dump. Fields not needed by the current typed extraction remain recoverable from the original artifact.

### 8.5 Original artifact preservation

The exact received bytes are durable evidence.

For a new artifact:

1. copy the exact received bytes to a RideWorks-managed staging file while computing SHA-256 and size;
2. do not decompress/recompress or otherwise rewrite the preserved original;
3. parse from the RideWorks-managed staged/preserved bytes;
4. after successful validation/extraction, place the exact bytes in the deterministic durable originals location;
5. record hash, size, packaging, format, and stored path;
6. verify stored bytes match the recorded hash.

The implementation may vary the exact transaction/staging mechanics, but a failed import must not leave a completed Activity/Source whose extraction is incomplete or invalid.

An orphaned temporary/staging file may be cleaned safely. Do not overwrite a previously established original artifact silently.

### 8.6 Import identity and repeat-import behavior

Exact-artifact repeat import is in scope.

When the exact received bytes have a SHA-256 already associated with an established Source:

- do not create a new Activity;
- do not create a new Source;
- return the existing Activity/Source identity;
- report that the artifact was already imported;
- verify that the established stored original still exists and matches expected integrity metadata.

If the database says the exact artifact exists but its stored original is missing or fails integrity verification, fail with a clear integrity error. Do not silently overwrite/repair established evidence as part of ordinary import.

P1-01 does **not** reconcile different artifacts that may describe the same ride.

Different gzip packaging, a differently encoded FIT file, or another source file with different bytes may therefore remain a separate Activity in P1-01. This is an explicit phase boundary, not a universal reconciliation rule.

Do not infer same-ride identity from filename alone.

### 8.7 Import success/failure behavior

Define a completed import so that the application never exposes a successful Activity whose Source/extraction is only partially written.

For a new import, success requires at minimum:

- durable Activity;
- durable Source association;
- verified stored original artifact;
- successful typed extraction;
- current extraction identity;
- required persisted session/record/timing evidence.

Use a SQLite transaction for database-side atomicity.

If parsing/validation fails before completion:

- do not leave a completed Activity/Source;
- return a clear failure;
- preserve no misleading normalized evidence.

If database persistence fails after the original has been staged/moved, clean newly created unreferenced files when safe. Never remove an original already referenced by an established Source.

Do not build a general job/retry framework.

### 8.8 Re-extraction from preserved original

Provide a callable operation/CLI command to rebuild the current normalized extraction for an established Source **without the external input file**.

Expected behavior:

1. locate the Source's application-managed original;
2. verify its hash/size before parsing;
3. parse the preserved original;
4. create a new extraction identity/revision and complete replacement normalized evidence in a transaction;
5. only make the new extraction current after all new evidence is valid/persisted.

If re-extraction fails:

- retain the previous current extraction unchanged;
- do not create a new Activity;
- do not create a new Source;
- do not leave a half-current extraction.

The operation does not need generalized historical extraction retention in P1-01.

### 8.9 Retrieval boundary for P1-02

Provide a small application-level read interface that P1-02 can use without:

- importing the retired Strava application;
- reading research-report JSON;
- directly reparsing the external source file;
- embedding SQL throughout analysis code.

The read boundary must be able to retrieve by Activity ID/Source ID as appropriate:

- Activity/Source identity and artifact metadata;
- current extraction identity/version;
- source/session summary;
- ordered native record timestamp + power + HR evidence;
- power/HR availability counts;
- relevant lap/event timing.

Keep this simple. Do not build a generic repository framework.

### 8.10 Minimal CLI

Provide a small CLI through the RideWorks package, expected behavior approximately:

```bash
python -m rideworks import-fit /path/to/activity.fit.gz
python -m rideworks inspect <activity-id>
python -m rideworks reextract <source-id>
```

Exact command spelling may differ slightly if the resulting interface is clearer.

`import-fit` should print at minimum:

- imported vs already-imported status;
- Activity ID;
- Source ID;
- current extraction ID;
- data directory used.

`inspect` should provide a compact, privacy-conscious view useful for verification:

- Activity/Source IDs;
- artifact basename/hash/size/format/packaging;
- extraction parser/mapping versions;
- required session summary values and explicit missing values;
- record/power/HR counts;
- lap/event counts.

Do not dump raw streams or coordinates.

### 8.11 Extraction/mapping version

Create an explicit RideWorks extraction/mapping version for this normalized representation, for example a small constant such as `fit-v1` or equivalent.

It must change later when extraction semantics materially change.

Parser package version and RideWorks extraction/mapping version are separate facts.

### 8.12 Legacy code boundary

- legacy loader behavior that substitutes zero for missing data;
- legacy MariaDB/application startup path;
- legacy FTP fallback/training-load behavior;

- old launcher exposure/binding behavior.

Research parsing utilities may be consulted for field names, observed file structure, and diagnostic evidence, but their compact report representation is not the RideWorks normalized import representation.

## 10. Verification / test procedure

### 10.1 Automated tests

Use privacy-safe synthetic inputs/fixtures and temporary data directories.

Automated tests must cover meaningful reusable behavior including at least:

#### Identity/durability

- new import creates one Activity and one Source;
- Activity ID differs conceptually from Source ID and artifact hash;
- exact same artifact imported again returns the same Activity/Source;
- repeat import remains idempotent after closing/reopening the store;
- stored original hash and size match imported bytes;
- application data remains retrievable from a new process/store instance.

#### Missingness/values

- legitimate zero power persists as zero;
- missing power remains missing rather than zero;
- missing HR remains missing rather than zero;
- a source summary field such as maximum HR can be persisted when present;
- missing required summary evidence remains explicitly missing;
- availability counts distinguish present, absent, and present-with-missing cases.

#### Timing

- source-record order is preserved;
- duplicate timestamps can coexist without sample loss;
- timestamps are not used as the sole record key;
- elapsed and timer duration remain distinct;
- lap/event ordering and timing survive extraction.

#### Failure

- invalid gzip fails without completed Activity/Source;
- invalid FIT fails without completed Activity/Source;
- unsupported multi-session/similarly ambiguous content fails clearly rather than selecting silently;
- failed database/extraction operation does not expose a partial completed import;
- failed re-extraction leaves the previous current extraction intact.

#### Re-extraction/versioning

- re-extraction uses the stored original, not the external input path;
- successful re-extraction preserves Activity/Source IDs;
- successful re-extraction changes current extraction identity/revision;
- parser version and RideWorks mapping version are persisted;
- read API exposes the current extraction identity.
